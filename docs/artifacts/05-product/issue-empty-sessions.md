# 问题记录：历史会话里大量「（无标题）0 轮」

日期：2026-11-26　｜　状态：已修复并清理历史数据　｜　影响范围：会话列表（`GET /sessions`）

---

## 1. 现象

侧栏历史里出现一长串「（无标题）· 0 轮」，时间从 03:22 到 07:22 不等，中间夹着正常会话。

用户视角：像是系统在自动创建对话，但点进去什么都没有。

---

## 2. 归因

### 2.1 数据侧证据

```sql
SELECT user_id, COUNT(*) total,
       SUM(CASE WHEN NOT EXISTS (SELECT 1 FROM message m WHERE m.session_id=s.id) THEN 1 ELSE 0 END) empty_cnt
FROM session s GROUP BY user_id;
```

| user_id | 总会话 | 空会话 |
|---|---:|---:|
| local（前端用的用户） | 39 | **22** |
| u1（早期租户测试） | 3 | 3 |
| eval / smoke / 其它 | 1800+ | 0 |

两个关键信号：

1. **空会话集中在 `local`**，说明是前端行为，不是评测脚本。
2. **多条记录创建时间精确到毫秒相同**（如 `13:45:03.506` 与 `.502`、`03:34:15.822` 两条），
   说明是**同一时刻的多次页面加载**——不是用户操作。开发期间预览面板随文件改动热更新，
   每刷新一次就建一条。

### 2.2 代码侧根因

三处都在"还没有对话"的时候就创建了会话：

| 位置 | 行为 | 后果 |
|---|---|---|
| `useSessions.restore()` | 没有 localStorage 或校验失败 → `createNew()` | 每次打开页面建一条 |
| `App.onMounted` | 依赖 restore 的返回值 | 同上 |
| `newChat()`（点"新对话"） | 立刻 `createNew()` | 点了不说话就多一条 |

`restore()` 的问题更隐蔽：它把**任何**异常都当成"会话不存在"。
后端重启时 `GET /sessions/{id}` 短暂 502，也会被判成会话丢失 → 新建一条，旧会话被孤立。

### 2.3 展示侧放大了问题

`listByOwner` 没有任何过滤，0 条消息的会话照样返回，前端只能显示「（无标题）· 0 轮」。

---

## 3. 修复

### 3.1 会话改为惰性创建（核心）

会话只在**用户发出第一条消息**时存在。

| 改动 | 说明 |
|---|---|
| `restore()` | 只认领已有会话，校验失败就把 `currentId` 置空，**不再新建** |
| `newChat()` | 改为 `reset()`：清空当前会话 + 删 localStorage，不建会话 |
| 新增 `ensure()` | 首次发送前调用：有会话直接用，没有才 `POST /sessions` |
| `useChat.send(sessionId, ...)` | 会话 id 由调用方传入，composable 不再自己解析 |
| `ChatView` | 无会话时直接渲染空态；`watch(sessionId)` 区分"自己刚建的"和"用户切换的"，避免发送中被清空 |

### 3.2 列表过滤空会话（防御）

```sql
AND EXISTS (SELECT 1 FROM message m2 WHERE m2.session_id = s.id)
```

内存模式同步加 `filter(s -> s.turnCount() > 0)`，两条路径口径一致。

即使将来又出现脏数据，也不会显示在历史里。

### 3.3 清理历史数据

只删「没有任何消息」的会话——这类行不含任何用户内容，删除不丢数据：

```sql
DELETE s FROM session s
WHERE NOT EXISTS (SELECT 1 FROM message m WHERE m.session_id = s.id);
```

执行结果：**删除 26 条**（22 条 local + 3 条 u1 + 1 条其它），剩余 1899 条会话、7657 条消息。

脚本：`.data/ops/CleanupEmptySessions.java`（JDBC 直连，不经过应用）。

### 3.4 顺带修复：时间显示差 8 小时

截图里的 `07:22` 实际是本地 `15:22`。

- 数据库 `time_zone=SYSTEM`，而宿主机是 UTC，`NOW()` 存的是 UTC
- 列类型是 `DATETIME`（无时区），JDBC 的 `serverTimezone` 不参与转换
- 前端按本地时间直接截字符串，就差了 8 小时

修复：接口返回 ISO-8601 UTC（`2026-11-26T07:30:34.009Z`），前端用 `new Date()` 转本地再显示。
**存储仍是 UTC**，不引入时区迁移。

## 5. 防回归

1. **列表过滤有单测**（内存路径），SQL 路径由 `EXISTS` 保证，逻辑对称。
2. **会话创建只有一个入口**：`ensure()`。任何新功能需要会话时都必须走它，
   不允许再出现"页面加载即建会话"。
3. 如果以后加"会话自动命名"，也必须在首条消息之后，否则又会回到同一个坑。

---

## 6. 一句话总结

空会话不是数据问题，是**生命周期问题**：会话在"打开页面"时被创建，而不是"开始对话"时。
把它推迟到第一条消息，问题从源头消失；列表过滤只是第二道防线。

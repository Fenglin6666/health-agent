## 问题 1 · 架构检查空转（P0）

**位置**：`ArchitectureTest.java:32`

```java
slices().matching("com.health.agent.(manager|execute)..")
        .should().notDependOnEachOther();
```

**问题**：`manager` 包不存在（manager 是 `ExecuteAgents` 里的一个名字，不是包）。切片只剩 `execute` 一个，`notDependOnEachOther` 对单切片恒真。

**影响**：这条规则从写下的那天起就没拦过任何东西。看起来有三条架构约束，实际只有两条在工作。

**这是最危险的一类问题**：不是"没检查"，是"以为检查了"。

**修复**：改成约束真正的隔离边界——能力层与适配层之间互不依赖。

```java
slices().matching("com.health.agent.(safety|memory|report|knowledge|integration)..")
        .should().notDependOnEachOther();
```

理由：这五个包都在 L1/L2，按详细设计 `00-总览` 的依赖图，它们之间不应该有直接依赖，协作由 `execute` 编排。

## 问题 2 · 域外拦截不写事件（P1）

**位置**：`ChatController.java:360`（`finish(String text, ...)` 重载）

**问题**：域外请求走 String 重载，只 `emit token + done`，不写 `turn_start` / `turn_end`。

**复现**：冒烟用例「今天天气怎么样」→ `agents=[]`，`status=running`。

**影响**：

1. 统计失真：域外请求不出现在事件表，拦截率无法从 `turn_event` 算
2. 运维误判：`timeline` 永远停在 `running`，看起来像"卡住了"

**修复**：在该重载里补一对事件，与 `KernelResult` 路径对齐。

## 问题 3 · 详细设计与实现不符（P2）

**位置**：`docs/spec/detail/04-memory.md` 第 5.4 节

**文档写**：「默认取决于配置，必须写死 JDBC」。

**实现是**：`PersistenceConfig` 的默认值已经是 `jdbc`（`${ha.persistence.mode:jdbc}`），且类注释明确写了「默认连不上就启动失败，不自动降级」——理由也写了：降级到内存是"看起来能用"的假状态，比启动失败更危险。

**结论**：实现比文档更严谨。文档描述的是一个不存在的隐患，会误导后来人去"修"一个已经修好的东西。

**修复**：改文档，如实描述现状，保留"显式开关"的说明。

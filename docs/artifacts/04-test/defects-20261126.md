### D-010 · DSML 工具调用标记泄漏到用户可见文本（已修）

**严重度**：高　**归因**：`product`　**状态**：已修，待真实请求复验

**现象**：手工提问「附近的大医院」，前端显示 `< || DSML || parameter>` 一类原始标记，`find_care` 实际没有执行。

**归因（三层，逐层都能拦但都没拦）**：

1. **模型层**：请求不带原生 `tools` 参数（`OpenAiCompatibleClient` 有意为之），但 system prompt 里有完整工具清单和参数 schema。DeepSeek-V4 的 DSML 是 tokenizer 层面的固有模式，看到工具语义就发射；与 `response_format: json_object` 的约束冲突后退化——实测形态带空格、半角竖线，与标准格式 `<｜｜DSML｜｜...>` 已不一致。
2. **解析层（根因）**：`extractJson()` 从脏文本里抠出第一个 `{` 到最后一个 `}`，得到合法 JSON，`readTree()` 成功，但里面没有 `decision` 字段，`switch` 落到 `default`，返回的是 `rawContent`（原始全文）而不是抠出来的 `json`。**解析"成功"了，所以 `max-retries` 一次都没触发**——兜底分支吞掉了本该重试的信号。
3. **渲染层**：`answer.text()` 非空即返回，跳过流式重生成。

**处置**：

- 新增 `ProtocolMarkup`：匹配 DSML 特征，容忍空格、全半角竖线、单双竖线（退化形态比标准格式多）
- `DecisionParser.parse()` 入口拦截，命中则返回 `Answer(null)`，交回内核走流式重生成——那条路径不带工具清单，不会再次进入工具调用模式
- **不做 DSML 解析执行**：医疗场景下，从畸形文本里还原工具调用并执行，错一次就是事故。宁可重生成，不可猜参数

**验证**：`DecisionParserTest` 8/8（新增 3 条：退化形态、标准形态、纯文本不误伤）；全量单测 49/49；`ArchitectureTest` 3/3；`mvn clean package` 成功。

**已知残留**：流式回答路径（`AgentKernel.streamAnswer`）未加硬守卫。该路径不带工具清单，触发概率低；且流式 token 一旦推出无法撤回，加守卫需要缓冲首包，收益不抵复杂度。列为观测项，复现再修。

**这条缺陷的方法论价值**：它不是"模型偶尔抽风"，而是**兜底策略的语义错误**——把"格式不符"降级成"当纯文本回答"，等于让内部协议获得了对外发言权。同类风险存在于任何"解析失败就原样返回"的地方，值得全项目扫一遍。

# 流程总览

这份文档定义项目的五阶段研发流程，以及每个阶段的**入口、产物、出口门禁**。

它的用途只有一个：任何时候你都能回答"现在走到哪了、下一步该产出什么、什么算通过"。

---

## 0. 为什么按阶段管

过程产物是**方向**：需求定错了，后面全错；方案定错了，代码白写。所以它们不能和代码混在一起，也不能彼此混在一起——否则出问题时不知道该回退到哪一层。

按阶段分目录的直接好处：

- **回退有落点**：路由不准，回退到 `01-需求` 还是 `02-方案`，看门禁卡在哪一层
- **缺失看得见**：某个阶段目录是空的，就是没做，不用翻文档猜
- **交接有契约**：每个阶段的出口就是下一阶段的入口，产物不齐不能往下走

## 2. 阶段定义

### 阶段 1 · 需求生产 → `01-需求/`

| 项 | 内容 |
|---|---|
| 谁做 | 人工提需求，Agent 整理成规格 |
| 入口 | 用户痛点、竞品差距、线上问题 |
| 产物 | 需求规格（做什么/不做什么/P0-P1-P2 分级） |
| 出口门禁 | 每条 P0 都有可判定的验收标准；明确写了"不做什么" |
| 失败回路 | 需求说不清 → 退回重写，不进方案 |

**当前产物**

| 文件 | 性质 |
|---|---|
| `PRD.md` | 产品需求文档 v1.0，讲决策理由与用户场景，对外可评审 |
| `主需求-需求规格.md` | 主需求 v1.2，P0/P1/P2 分级与验收标准 |
| `增量-v1.3-交互能力.md` | 增量需求（复制/反馈/分享/追问卡片/会话/可靠性） |
| `增量-FR21-图片粘贴.md` | 增量需求（图片粘贴与 OCR） |
| `输入/竞品对照.md` | 需求来源：与小荷 AI 医生的逐项对照 |
| `输入/用户问题/issue-*.md` | 需求来源：三个线上问题的归因记录 |

**为什么 issue 放在需求阶段**：问题记录不是归档，是需求的输入。放在这里，"问题 → 需求"的链路不用跨目录找。

---

### 阶段 2 · 方案确认 → `02-方案/`

| 项 | 内容 |
|---|---|
| 谁做 | Agent 出方案，人工评审 |
| 入口 | 阶段 1 的需求规格 |
| 产物 | 概要设计（服务怎么拆）+ 技术方案（怎么落地）+ 域规格（每个域怎么实现）+ 详细设计（类与方法签名） |
| 出口门禁 | 每条 P0 需求都能在详细设计里找到落点；跨域契约写清楚 |
| 失败回路 | 方案评审不过 → 退回改方案，不动代码 |

**四层结构**，越往下越具体：

| 层 | 目录 | 回答什么 | 读者 |
|---|---|---|---|
| 概要 | `概要设计.md` | 服务怎么拆、域怎么分、数据模型 | 架构 |
| 方案 | `技术方案.md` | 部署、选型、跨域契约 | 开发 |
| 域规格 | `域规格/00–11` | 每个业务域怎么实现、怎么测、边界在哪 | 开发 + 测试 |
| 详细 | `详细设计/00–12` | 有哪些类、方法签名、边界怎么处理 | 开发 |

**增量需求走旁路**：`增量-v1.3-交互能力.md`、`增量-FR21-图片粘贴.md` 与 `01-需求/` 下的同名文件一一配对，改增量时不改主规格。

---

### 阶段 3 · Coding + 测试内循环 → `03-开发/`

| 项 | 内容 |
|---|---|
| 谁做 | Agent 写代码，人工审 |
| 入口 | 阶段 2 的详细设计 |
| 产物 | 代码 + 代码评审（CR）+ 构建日志 |
| 出口门禁 | `mvn clean package` 通过、单测全绿、ArchUnit 架构规则不破 |
| 失败回路 | 编译/单测/CR 任一失败 → 回到编码 |

**当前产物**

| 文件 | 内容 |
|---|---|
| `代码评审/CR-20261126-001~005.md` | 5 份 CR：全量评审、拆网关、交互能力、图片粘贴、移除报告页 |
| `构建日志/build-20261126-baseline.log` | 基线构建，CR-001 的依据 |
| `构建日志/build-20261126-r2~r17.log` | 16 轮迭代构建，共 1622 行 |

**构建日志为什么要入库**：CR 里写的"33 个单测通过"不是结论，是结论的引用。日志在，才能复核；日志不在，CR 就是自说自话。

---

### 阶段 4 · 测试准备 → `04-测试准备/`

| 项 | 内容 |
|---|---|
| 谁做 | Agent 出用例，人工评审 |
| 入口 | 阶段 1 的验收标准 + 阶段 2 的域规格 |
| 产物 | 测试策略与用例、测试数据、探针脚本 |
| 出口门禁 | 每条 P0 验收标准都有对应用例；数据覆盖各场景；探针能跑 |
| 失败回路 | 用例评审不过 → 补用例，不进外循环 |

**当前产物**

| 文件 | 内容 |
|---|---|
| `测试策略与用例.md` | 六类测试的分工与判定口径 |
| `测试数据/medical-agent-5000-questions.csv` | 5000 条语料（另有同名 `.md` 版本） |
| `探针/smoke.py` | 冒烟探针 |
| `L1评测集交付说明.md` | L1 四域（sc/ks/ri/nv）42 条过程用例的落地说明 |

**这个阶段是流程图上明确有、但之前项目里没有独立位置的。** 5000 条数据原来扔在 docs 根下的 `test-data/`（旧位置，已废弃），和流程节点对不上；现在归到这里。

---

### 阶段 5 · 测试外循环 → `05-测试执行/`

| 项 | 内容 |
|---|---|
| 谁做 | Agent 跑测试，人工判门禁 |
| 入口 | 阶段 4 的用例与数据 + 可运行的构建 |
| 产物 | 执行报告、缺陷单、验收单、门禁结论、原始结果 |
| 出口门禁 | 六项门禁全过 + P0 逐条验收通过 |
| 失败回路 | 门禁不过 → 退回阶段 3 改代码 |

**六项门禁**（阈值写死在需求规格里，不临时调）

| # | 指标 | 阈值 |
|---|---|---|
| 1 | 红旗召回 | 100% |
| 2 | 主路由准确率（Pass^3） | 100% |
| 3 | 多意图覆盖 | ≥60% |
| 4 | 多段落库 | 100% |
| 5 | 降级率 | ≤5% |
| 6 | 首段延迟 | P95 ≤6s |

**当前产物**

| 文件 | 内容 |
|---|---|
| `执行报告/test-run-20261126.md` | r9 外循环执行报告，对运行中的 jar 发真实请求 |
| `执行报告/smoke-*.md` | 3 轮冒烟 |
| `缺陷与验收/defects-20261126.md` | 缺陷单，六分类归因 |
| `缺陷与验收/acceptance-20261126.md` | 验收单，P0 逐条判定 |
| `门禁/gate-20261126.md` | 门禁报告（**r9 结论已过期**） |
| `结果/*.json` | 原始评测结果，8 项 |

**判定证据只有两份有效**：`route-eval-pass3-r3.json`、`redflag-20261126.json`。其余要么过期、要么因余额不足作废。

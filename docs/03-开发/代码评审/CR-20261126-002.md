# CR-20261126-002 · 拆出 llm-gateway

日期：2026-11-26　｜　范围：新增 `llm-gateway` 模块 + core 的模型接入配置　｜　结论：**通过（行为验证受余额阻塞）**

---

## 1. 变更意图

按 `03-技术方案` 的拆分顺序，第一步抽 `llm`（无状态、切口最小）。

**拆的不是代码，是信任边界。** 之前 core 进程里同时有业务逻辑和模型密钥；
拆完之后 core 只有"往哪儿发"，密钥、上游供应商、兜底模型全部落在网关。

协议保持 OpenAI 兼容，所以 core 的 `OpenAiCompatibleClient` 业务代码一行没改，
只多了一个 `X-Internal-Token` 请求头。

---

## 2. 改了什么

### 新增 `llm-gateway`（独立进程 :8081）

| 文件 | 职责 |
|---|---|
| `GatewayApplication` | 启动入口 |
| `GatewayProperties` | 上游地址、密钥、兜底模型、内网令牌 |
| `ChatCompletionsController` | OpenAI 协议透传（流式 + 非流式）、兜底重试、token 计量 |
| `application.yml` | 端口 8081，上游与密钥全部来自环境变量 |

三条实现约束，都写进了代码注释：

1. **流式不缓冲**：上游吐一个 chunk 就往下游写一个。攒完再发等于把流式变成长连接。
2. **错误原样透传**：402/429/5xx 的状态码和正文都要给回 core，否则 core 分不清"没钱"和"网关挂了"。
3. **流式不重试**：已发出的 token 收不回来，重试会让用户看到两遍开头。兜底只对非流式生效。

### core 侧

| 文件 | 改动 |
|---|---|
| `LlmProperties` | 加 `internalToken`；`isOfflineEffective()` 改为**只认显式开关** |
| `OpenAiCompatibleClient` | 配了内网令牌时加 `X-Internal-Token` 头 |
| `application.yml` | 默认 base-url 指向 `:8081/v1`；密钥移出；超时 30s → 60s |
| `README` | 启动顺序、环境变量表、离线语义 |
| `08-跨域契约` | 新增 core → 网关、网关 → 上游两段契约 |
| `03-技术方案` / `09-模块划分` | 服务状态从"待拆"改为"已拆"，补实际做法 |

### 一个必须说的行为变更

**离线模式不再按"有没有密钥"推断。**

旧逻辑：`apiKey` 为空 → 自动走离线桩。
拆出网关后 core 本来就没有密钥，旧逻辑会让它**静默走桩**——用户看到一堆模板回答，日志里没有任何错误。

新逻辑：只有 `HA_LLM_OFFLINE=true` 才走桩。没配网关也没配密钥 → 连接失败。
宁可报错，不要假装能用。

## 3. 验证

### 单测：47 个全过

| 模块 | 数量 | 新增 |
|---|---:|---|
| health-agent | 42 | L1 断言语义 8 条 |
| llm-gateway | 5 | 透传 / 错误透传 / 流式 / 兜底 / 鉴权 |

网关的 5 条用 JDK 自带 `HttpServer` 当假上游，不起 Spring 上下文——测的是字节有没有原样过。

### 端到端：core → 网关 → 上游

账户余额为 0，正好用 402 验证整条链路：

```
core 日志: llm http 402: {"error":{"message":"Insufficient Balance",...}}
网关日志: llm model=deepseek-chat prompt_tokens=0 completion_tokens=0
```

两次请求（core 的重试）都在网关日志里，402 的正文原样回到 core。
**这证明链路通了**——换成余额正常的账号，同一条路就能拿到 200。

### 配置坑（实际踩到了）

第一次验证时 core 拿到 401，不是 402。原因是 shell 里还留着：

```
HA_LLM_BASE_URL=https://api.deepseek.com/v1
```

它覆盖了 `application.yml` 的默认值，core 绕过网关直连上游，又没有密钥 → 401。

**这不是 bug，是拆分后的必然结果**：环境变量优先级高于配置文件。
已写进 README：用网关时必须 `unset HA_LLM_BASE_URL HA_LLM_API_KEY`。

## 4. 没做的事，和为什么

### ops 没拆

`evaluation` 现在依赖三样在 core 进程内的东西：

| 依赖 | 用途 |
|---|---|
| `RedFlagScanner` | 红旗规则评测（纯规则） |
| `KnowledgeClient` | 事实校验、OTC 出处核对 |
| `ExecuteAgents` | 抽样路由评测 |

要拆就得先在 core 上开三个内部接口，等于为了拆服务而扩大 core 的对外面。
而且现在没有真实流量，ops 独立部署带来的是"多一套进程要起"，不是"故障隔离"。

**触发条件写进 09 模块划分**：等 L1 语料稳定、评测只走 HTTP 之后再动。

### gateway（鉴权/限流）没建

当前只有本地访问，没有多租户真实流量。建一个没有策略可执行的网关，只会多一层转发。

## 5. 风险

| 风险 | 影响 | 处置 |
|---|---|---|
| `HA_LLM_BASE_URL` 残留导致绕过网关 | core 直连上游，密钥回到进程里 | README 写明；部署时清空 |
| 流式只测了假上游 | 真实上游的分块边界可能不同 | 恢复余额后跑一次多意图（会产生 `continue` 两段流式） |
| 网关单点 | 它挂了全站不可用 | 与拆分前相同——原来 core 挂了也一样。不新增风险 |
| 内网令牌默认空 | 本地开发方便，部署时忘配就是裸奔 | `application.yml` 注释标"部署时必须配"；后续可加启动检查 |

---

## 6. 回滚

网关是纯透传，回滚只需要两个环境变量：

```bash
export HA_LLM_BASE_URL=https://api.deepseek.com/v1
export HA_LLM_API_KEY=sk-xxx
```

不需要改代码、不需要重新打包。这是选择"协议透传"而不是"语义网关"的直接收益。

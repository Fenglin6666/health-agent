## 1. 服务划分

### 1.1 3+2 划分

| 服务 | 职责 | 包含的包 | 状态 |
|---|---|---|---|
| **core** | 在线链路：接入、编排、四能力、记忆、安全 | platform / execute / kernel / memory / safety / report / routing / integration | 单体，待拆 |
| **knowledge** | 知识检索与图谱校验 | `knowledge-service`（Python） | 已独立 |
| **ops** | 评测跑批、配置发布、badcase | evaluation | 单体，待拆 |
| **llm-gateway** | 模型接入、降级、计量 | `llm-gateway`（独立进程 :8081） | ✅ 已拆 |
| **gateway** | 鉴权、限流、路由 | 无（当前直连） | 未建，可选 |

**为什么 core 不拆**：四能力共享同一份会话状态和记忆，拆开就要解决分布式事务。当前规模下，模块边界比进程边界更重要。

**llm-gateway 拆出去了什么**：不是把 `llm` 包的代码搬走，是把**凭证和上游地址**搬走。
core 只认 `base-url` 一个配置，密钥、上游供应商、兜底模型全部落在网关。协议仍是 OpenAI 兼容，
所以 core 的客户端一行没改（只多了一个内网令牌头）。这是"切口最小"的具体含义——
改的是部署形态和信任边界，不是业务代码。

### 1.2 边界判据

不是按业务域切，是按**变更频率 + 故障隔离**切：

| 服务 | 变更频率 | 故障影响 | 结论 |
|---|---|---|---|
| core | 高（prompt、路由规则） | 全站不可用 | 保持单体，内部模块化 |
| knowledge | 低（知识数据更新） | 检索降级，可回退 | 独立，可单独扩缩 |
| ops | 中（评测集、门禁） | 不影响在线 | 独立，挂了不影响用户 |
| llm-gateway | 低（模型切换） | 全站不可用 | 独立，便于多模型灰度 |

**判据**：如果一个模块挂了会让用户立刻感知，它就该和主链路同进程（core）；如果挂了只是少个功能，它可以独立。

### 1.3 依赖方向

```
gateway ──> core ──> llm-gateway
              │
              ├──> knowledge
              └──> ops（只写事件，不反向依赖）

禁止：core ← knowledge（知识服务不能回调 core）
禁止：llm-gateway ← core（模型层不认识业务）
```

**依赖只能单向**。反向依赖一旦出现，拆服务就变成了分布式单体。

## 2. 数据模型

### 2.1 库划分

| 库 | 归属 | 表 |
|---|---|---|
| `health_agent` | core | session / message / turn_event / fact_ledger / fact_current / contradiction / user_habit |
| `health_agent_ops` | ops | eval_run / eval_result / badcase / config_release |
| ES 索引 | knowledge | 药品、指标、疾病（已有） |
| Neo4j | knowledge | 图谱校验（已有） |

**不跨库 join**。core 需要 ops 的数据时，走接口或事件，不直连。

### 2.2 核心表

#### session

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | VARCHAR(32) | ULID，前缀 `sess_` |
| `tenant_id` | VARCHAR(64) | 租户 |
| `user_id` | VARCHAR(128) | 用户 |
| `active_agent` | VARCHAR(32) | 上一轮持有者，决定下一轮从谁开始 |
| `created_at` / `updated_at` | DATETIME(3) | — |

**`active_agent` 是核心字段**。多轮从它续接，不重新过 Manager。

#### message

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT | 自增 |
| `tenant_id` | VARCHAR(64) | 冗余存储，避免每次 join session |
| `session_id` | VARCHAR(32) | — |
| `turn` | INT | 第几轮 |
| `seq` | INT | 轮内序号 |
| `role` | VARCHAR(16) | USER / ASSISTANT / TOOL |
| `name` | VARCHAR(64) | 产生这条消息的 agent |

索引：`UNIQUE(tenant_id, session_id, seq)`。

**为什么冗余 `tenant_id`**：靠 `session_id` 关联也能隔离，但每个查询都要 join，而且漏写 join 条件就是跨租户泄露。冗余一列，换掉一整类风险。

#### turn_event

| 字段 | 类型 | 说明 |
|---|---|---|
| `tenant_id` | VARCHAR(64) | 冗余，理由同 message |
| `session_id` / `turn` / `seq` | — | 定位 |
| `type` | VARCHAR(32) | turn_start / agent_start / route / handoff / tool_start / tool_end / answer / turn_end |
| `agent` | VARCHAR(32) | 事件发生时谁在处理 |
| `detail` | JSON | 事件载荷 |

**这是排障的唯一依据**。没有它，只能看到"用户说了什么、最后回了什么"，中间全是黑盒。

#### fact_ledger（append-only）

| 字段 | 类型 | 说明 |
|---|---|---|
| `owner` | VARCHAR(200) | `tenant:user` |
| `fact_type` | VARCHAR(32) | allergy / medication / condition / habit |
| `fact_key` | VARCHAR(128) | 事实名 |
| `fact_value` | VARCHAR(512) | 事实值 |
| `confidence` | DECIMAL(4,3) | 抽取置信度 |
| `evidence` | VARCHAR(1024) | 原文片段 |
| `session_id` | VARCHAR(32) | 来源会话 |

**只追加不更新**。修订通过新增一条实现，`fact_current` 指向最新。

#### fact_current（投影）

`PRIMARY KEY(owner, fact_key)`，`ledger_id` 指回账本。

**投影可重建**。任何时候删掉它，都能从 `fact_ledger` 重放出来——这是 append-only 的价值。

#### contradiction

| 字段 | 说明 |
|---|---|
| `kind` | value_conflict / temporal_conflict |
| `severity` | high / medium / low |
| `old_value` / `new_value` | 冲突双方 |
| `status` | open / confirmed / dismissed |

**必须能追溯到两条冲突的 Fact**，不能只记结论。

### 2.3 约束

| 约束 | 实现 |
|---|---|
| 会话删除级联 | 外键 + 软删标记，事实账本一并标记 |
| 事件表增长 | 按月分区，保留 90 天 |
| 事实账本增长 | 不分区，永久保留（它是用户健康历史） |

---

### 2.4 租户隔离的实现约束

#### 租户表

| 字段 | 说明 |
|---|---|
| `tenant_id` | 主键 |
| `name` | 展示名 |
| `config_version` | 指向配置版本，不复制配置 |
| `status` | active / suspended / deleted |
| `created_at` | — |

#### 配置版本

| 字段 | 说明 |
|---|---|
| `version` | 主键，如 `cfg_20261126_01` |
| `rule_pack_hash` | 规则包内容哈希 |
| `prompt_hash` | prompt 集合哈希 |
| `kb_version` | 知识库版本 |
| `published_at` | — |

**租户只存指针**。改配置 = 发布新版本 + 改指针，不批量改 N 个租户。

#### 三条实现约束

| 约束 | 做法 | 防的是什么 |
|---|---|---|
| 查询强制带租户 | DAO 入口统一注入，SQL 层不接受无租户的查询方法 | 漏写条件导致跨租户泄露 |
| 缓存 key 带前缀 | `t:{tenantId}:sess:{sessionId}` | 缓存击穿租户边界 |
| 身份不信请求头 | 凭证 → tenantId，`X-Tenant-Id` 只在本地开发启用 | 构造 header 越权 |

**第三条是当前的真实漏洞**。修复优先级高于本方案的其他任何一项。

## 3. 接口与通信

### 3.1 同步 vs 异步

| 交互 | 方式 | 理由 |
|---|---|---|
| 用户 → core | HTTP + SSE | 需要流式 |
| core → knowledge | HTTP（同步） | 检索必须在生成前完成 |
| core → llm-gateway | HTTP（同步，流式透传） | 首 token 依赖它 |
| core → ops | 事件（异步） | 评测不该拖慢在线 |
| ops → core | 只读接口 | 跑批需要真实链路 |

### 3.2 契约管理

- 对外 API：OpenAPI 描述，放在 `contracts/openapi/`
- 服务间：JSON Schema，放在 `contracts/schema/`
- **契约变更必须版本化**，不允许静默改字段语义

## 4. 部署形态

### 4.1 本地开发

```
docker-compose: MySQL(3307) / Redis(6379) / ES(9200) / Neo4j(7474)
进程：core(8080) / knowledge(8001) / ops(8082，可选)
```

**中间件缺失时的行为**（NFR-03）：

| 缺失 | 行为 |
|---|---|
| ES / Neo4j | knowledge 回退内存实现，检索质量下降但不阻断 |
| MySQL | core 启动失败（会话和事实必须落库） |
| Redis | 会话缓存失效，走 DB |

### 4.2 单机部署

三个进程 + systemd。适合个人使用和演示。

### 4.3 容器

每个服务一个镜像，compose 编排。**不引入 K8s**——单机规模用不上，只会增加调试成本。

## 5. 拆服务迁移路径

### 5.1 顺序

```
阶段 0  保持单体，跑通内循环（CR + 门禁）
   ↓
阶段 1  抽 llm-gateway（无状态，切口最小）
   ↓
阶段 2  抽 ops（离线，不影响在线）
   ↓
阶段 3  knowledge 保持独立（已是）
   ↓
阶段 4  core 保持单体，内部模块边界收紧
   ↓
阶段 5  gateway（可选，按需）
```

**为什么先抽 llm-gateway**：它无状态、无业务逻辑、接口简单。抽错了回滚成本最低。

**为什么 core 最后不动**：它有状态（会话、记忆），拆它要解决分布式事务。当前规模不值得。

### 5.2 每次拆分的验收

拆服务本身是一次受控变更，必须走完整流程：

| 步骤 | 产物 |
|---|---|
| 拆之前 | 基线跑批结果（`eval_run` 快照） |
| 拆分中 | CR 报告（接口是否等价、有无隐式共享状态） |
| 拆之后 | 同一套用例回测，与基线 diff |
| 判定 | 无新增失败，且 P95 延迟退化 ≤10% |

**没有基线就不许拆**。拆完出问题无法归因，只能整体回滚。

### 5.3 回滚

每个阶段独立可回滚：配置开关切回单体调用路径，不重新部署。

## 6. 关键决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 服务粒度 | 3+2 | 单人维护上限；开源医疗系统（Medplum/OpenMRS）都是 1 个后端，3+2 已经偏多 |
| 库划分 | core / ops 分库，knowledge 用 ES | 在线与离线隔离；知识本来就是异构存储 |
| 通信 | HTTP + SSE，不引入 MQ | 当前没有需要削峰的场景，MQ 只会增加运维面 |
| 部署 | 容器但不 K8s | 单机规模，K8s 的调度能力用不上 |
| 拆服务时机 | 先跑通内循环 | 没有基线就拆，出问题无法归因 |

## 7. 待确认

| # | 待确认 | 影响 | 建议 |
|---|---|---|---|
| 1 | `gateway` 是否真的需要 | 本地开发可省，线上需要鉴权限流 | 阶段 5 再定，先不建 |
| 2 | `ops` 是否需要独立库 | 数据量小的话可以同库不同表 | 先同库，跑批数据超过 100 万行再分 |
| 3 | 记忆模块默认实现 | 决定数据是否真落库 | 详细设计里明确，默认 JDBC |
| 4 | `turn_event` 分区策略 | 影响查询与归档 | 按月分区，保留 90 天，先不做归档 |
| 5 | 租户身份用什么凭证 | 决定鉴权实现 | JWT（claim 带 tenant_id），本地开发允许 header 但需显式开关 |

## 1. 目标与范围

### 1.1 本期目标

不是"功能更多"，是**把研发流程走完**：五类产物齐全，内循环与外循环各跑通一次。

### 1.2 范围

| 在范围内 | 不在范围内 |
|---|---|
| 四类咨询能力（症状/用药/报告/就医） | 语音输入 |
| 意图路由与多意图处理 | 多科室专家会诊 |
| 安全闸门（红旗/域外/输出审查） | 处方流转、挂号下单 |
| 记忆与矛盾检测 | 影像原图判读 |
| 3+2 服务拆分 | 计量计费 |
| **多租户隔离（数据 + 身份 + 配置版本）** | 租户自助开通 |

### 1.3 一条贯穿全系统的约束

**安全判断先于业务判断。** 任何链路设计，只要出现"先分类再考虑要不要急救"，就是错的。

## 2. 名词与角色

### 2.1 名词

| 名词 | 含义 | 容易混的点 |
|---|---|---|
| **能力（capability）** | 一种处理咨询的职责，当前 4 种 | 不是"科室"，不按医学专科划分 |
| **路由（route）** | 判断这句话交给哪个能力 | 与"交接（handoff）"走同一条路径，区别只在谁发起 |
| **交接（handoff）** | 执行中的能力把问题转给另一个能力 | 会多一次模型调用 |
| **remaining** | Manager 拆出的、主诉求之外的其他诉求 | 最多 2 条，不是无限拆 |
| **红旗** | 必须立即就医的信号 | 与"危急值"不同：红旗是症状描述，危急值是检验数值 |
| **六段式** | 结论的固定结构 | 缺任一段即判定失败 |
| **档位（tier）** | 风险分级 | 与"严重程度"不是一回事，档位是行动建议的依据 |

### 2.2 角色

| 角色 | 职责 | 不做 |
|---|---|---|
| **Manager** | 只做一次判断：交给谁 / 追问 / 直接答 | 不回答健康问题本身 |
| **Execute（4 个）** | 各自领域的实际处理 | 不判断"这句话该归谁"（Manager 的活） |
| **Safety** | 红旗、域外、输出审查 | 不参与意图判断 |
| **Memory** | 事实账本、画像投影、矛盾检测 | 不参与回答生成 |

## 3. 系统架构

### 3.1 分层全景

```
┌──────────────────────────────────────────────────────────┐
│ 接入层   ChatController                                   │
│          · SSE 流式  · 会话创建  · 时间线查询              │
│          · 租户解析（凭证 → tenantId，不信请求头）         │
├──────────────────────────────────────────────────────────┤
│ 编排层   AgentRuntime                                     │
│          · 交接链  · 步数预算  · 事件落库  · 多意图队列    │
│          ├─ Manager（快模型，只跑一步）                    │
│          └─ Execute：doctor / pharma / report / care       │
├──────────────────────────────────────────────────────────┤
│ 能力层                                                    │
│   Safety      RedFlagScanner · OffTopicFilter · SafetyGate│
│   Memory      FactLedger · ProfileAggregator · Contradiction│
│   Knowledge   KnowledgeClient（远程）· 检索三层            │
│   Report      LabReference · 指标归一化                    │
│   Tenant      配置版本指针 · 规则包选择 · 配额（预留）      │
├──────────────────────────────────────────────────────────┤
│ 数据层   MySQL（会话/事实/事件，全部带 tenant_id）         │
│          Redis（会话缓存，key 带 tenant 前缀）             │
│          ES（检索）· Neo4j（图谱校验）                     │
├──────────────────────────────────────────────────────────┤
│ 外部     LLM（Manager 快模型 / Execute 强模型）            │
│          高德 POI  ·  Web Search                          │
└──────────────────────────────────────────────────────────┘
```

**分层的判据**：依赖只能向下。编排层不认识 SQL，能力层不认识 HTTP，接入层不认识 prompt。

### 3.2 一次问诊的时序

```
用户
 │ ① POST /sessions/{id}/messages
 ▼
ChatController
 │ ② RedFlagScanner.scan(text)        ← 毫秒级，规则
 │ ③ OffTopicFilter.check(text)       ← 毫秒级，规则
 │ ④ AgentRuntime.run(session)
 ▼
AgentRuntime
 │ ⑤ Manager.decide()                 ← 一次快模型调用
 │    ← ROUTE(doctor, remaining=[pharma])
 │ ⑥ doctor.run()                     ← 强模型 + 工具
 │    ├─ knowledge_search
 │    ├─ health_record
 │    └─ ANSWER（流式输出第一段）
 │ ⑦ 队列非空 → pharma.run()
 │    └─ ANSWER（流式输出第二段）
 │ ⑧ turn_end(status, handoffs, steps)
 ▼
ChatController
 │ ⑨ SafetyGate.review(text)          ← 输出审查
 │ ⑩ SSE done + 会话落库
 ▼
用户
```

**三个关键点**：

1. ②③ 在任何模型调用之前。规则拦住就不花钱。
2. ⑥⑦ 的回答**分别落库**。只存最后一段，下一轮谁都看不到自己说过什么。
3. ⑨ 在流式之后，这是已知缺陷：字已经到用户眼前，审查只能记录不能改写。

### 3.3 当前形态与目标形态

| 维度 | 当前 | 目标（v1.2） |
|---|---|---|
| 部署 | 单体，16 个包 | 3+2 服务 |
| 服务划分 | 无（同进程） | core / knowledge / ops + gateway / llm-gateway |
| 数据库 | 单库 | core 库 + knowledge 库 |
| 检索 | 远程 Python 服务 | 不变 |
| 拆分时机 | — | **先跑通内循环，再拆**（拆服务本身是一次受控变更） |

**为什么先不拆**：拆之前没有基线，拆出问题无法归因。而且拆服务正好可以用来验证内循环的门禁能不能卡住一次真实变更。

## 4. 数据模型

### 4.1 会话状态机

```
S0_IDLE ──首条消息──> S1_TRIAGE
S1_TRIAGE ──红旗命中──> S2_HIGH_RISK ──┐
S1_TRIAGE ──未命中────> S3_COLLECT  <──┘
S3_COLLECT ──收敛────> S4_CONCLUSION
S4_CONCLUSION ──追问──> S5_DEEPEN ──补充──> S3_COLLECT
S4_CONCLUSION ──结束──> S6_ARCHIVE
```

转移表是纯数据，可单测、可回放。每次转移记 `from/to/reason/turn`。

### 4.2 核心实体

```
Session ──1:N── Message
   │                │
   │                └─ role: USER / ASSISTANT / TOOL
   │
   ├─1:N── TurnEvent（route / handoff / tool / answer / turn_end）
   │
   └─1:1── Profile（画像投影）
              │
              └─1:N── Fact（append-only 账本）
                         │
                         └─ 0:N ── Contradiction（待确认）
```

**三条不变量**：

1. `Fact` 只追加不覆盖。修订通过新增一条 + 指向被修订的 ID。
2. `TurnEvent` 是排障的唯一依据。会话内容回答"说了什么"，事件回答"怎么走到那句话的"。
3. `Contradiction` 必须能追溯到两条冲突的 Fact，不能只记结论。

## 5. 关键流程

### 5.1 意图路由

```
输入：用户原话 + 画像摘要
处理：Manager 一次模型调用，输出 JSON
输出：ROUTE{target, intent, remaining[]} | CLARIFY{question} | ANSWER{text}
```

**为什么不用规则做业务意图**：规则做"要不要送进模型"，模型做"送给谁"。混在一起会让规则表无限膨胀。

**判错的兜底**：接手的能力有交接权，发现不对可以转走。代价是多一次调用。

### 5.2 多意图串行

```
Manager 拆出 remaining
  → 主诉求执行完（ANSWER）
  → 队列非空？
      ├─ 是 → 交接给下一个，发 continue 事件
      └─ 否 → 结束
  → 中途 CLARIFY？
      └─ 把剩余写进历史（pending_kept），本轮结束
```

**为什么串行不并行**：医疗有依赖顺序——用药建议依赖病情判断。并行会让两边在不知道对方结论的情况下各说各话。

### 5.3 安全闸门

| 层 | 时机 | 手段 | 失败时 |
|---|---|---|---|
| 红旗 | 路由前 | 规则 | 注入提示，由模型组织语言（不套模板） |
| 域外 | 路由前 | 规则 | 直接返回固定话术 |
| 输出 | 生成后 | 规则 + 图谱校验 | `self` 模式记录，`public` 模式改写 |

**红旗为什么不用模板**：模板会"过度肯定"——系统只看到一句话，不知道是不是正在发生、是不是在转述别人的事。判断权给模型，规则只负责提醒它别漏。

### 5.4 记忆与矛盾

```
对话 → Librarian 抽取事实 → FactLedger 追加
                              │
                              ├─ 与 Profile 投影比对
                              │     └─ 冲突 → Contradiction（待确认）
                              │
                              └─ ProfileAggregator 重建画像
                                    └─ 注入下一轮 prompt
```

**为什么 append-only**：覆盖会丢历史，而"用户上个月说没过敏、这个月说青霉素过敏"本身就是重要信息。

---

### 5.5 租户隔离

```
请求 → 凭证解析 → tenantId → 上下文（不可变）→ 所有下游调用
```

**三层隔离，缺一层都不算做完**：

| 层 | 做什么 | 兜底位置 |
|---|---|---|
| **身份** | 从凭证解析租户，不信任请求头 | 接入层，解析失败直接 401 |
| **数据** | 所有查询强制带 `tenant_id` | 数据访问层统一注入，不靠每个方法手写 |
| **配置** | 每租户一个 `config_version` 指针 | 编排层加载 prompt/规则时按租户取 |

**为什么数据层要兜底**：应用层校验只能防"忘了加条件"的一半——漏一个查询就是跨租户泄露。把租户条件放进统一的 DAO 入口，漏不掉。

**为什么配置用指针不用副本**：N 个租户复制 N 套 prompt，改一次要改 N 处，必然漂移。指针指向同一份配置的不同版本，改配置只改一处。

## 6. 决策与待确认

### 6.1 已决策（详见 `health-agent-design.md` 的 18 条 ADR）

| 决策 | 一句话理由 |
|---|---|
| Manager + Execute 两级 | 路由用快模型，执行用强模型，成本和延迟都更优 |
| 不做科室交接 | 4 个能力已覆盖场景，按科室拆会让路由变成 20 分类 |
| Safety 不用 LLM | 可解释、可回归、毫秒级 |
| 会话不限轮次 | 截断等于逼用户重开，重开就丢上下文 |
| 中间件克制 | 能用 MySQL 就不引入新组件 |

### 6.2 待确认

| # | 待确认 | 影响 |
|---|---|---|
| 1 | 记忆模块默认用 InMemory 还是 Jdbc | 决定数据是否真的落库 |
| 2 | `public` 模式下流式输出如何改写 | 不改回缓冲，改写只作用于日志 |
| 3 | 3+2 拆分的具体边界（core 是否含 ops） | 影响部署与调试复杂度 |

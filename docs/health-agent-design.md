## 0. 一句话

一个个人向的健康管家 Agent：**以强制追问为核心交互，报告解读为入口，知识图谱为约束层，长期记忆为底座**，覆盖问诊、问药、报告、地点、科普五类能力。核心命题不是"能回答医疗问题"，而是——**让 LLM 在专业领域不出错，并且能证明它没出错**。

## 1. 目标、非目标与约束

### 1.1 三层目标

| 层次 | 具体内容 | 验收方式 |
|---|---|---|
| 能力目标 | 五类能力（问诊 / 问药 / 报告 / 地点 / 科普）共用一套内核与记忆；主链路"报告解读 → 风险识别 → 用药校验 → 档案沉淀 → 下次对话引用"跑通 | 主链路能完整演示 |
| 工程目标 | P95 < 6s、单次成本可归因、幻觉可检测 | 指标看板 + 评测报告 |
| 展示目标 | AI 应用深度（A）+ 平台架构（C） | 设计决策可讲清权衡 |

### 1.2 明确不做（非目标）

- **不做诊断结论**：所有输出是"信息整理 + 就医决策辅助"，不是诊断。模块命名同步改：不叫"诊断建议"，叫"可能性分析"。
- **不出处方**：不根据症状推荐处方药，不给剂量方案。但**允许查询说明书的客观用法**，也**允许推荐具体的非处方药（OTC）品种**（边界见 ADR-12）。
- **不做真实购药/问诊闭环**：没有供给能力，也没有药品经营资质。只做"附近药店/医院"的地点推荐，**不说"这家有货"**（没有库存数据）。
- **不做多节点高可用**：单机部署，目标是"能跑对"，不是"跑不死"。
- **不做医生端**：只有患者/家属视角。
- **不做实时网络检索**：医疗知识只从离线知识库出，不接"受控的网络 agent"（理由见 §7.5）。

### 1.3 风险提示（已决策：接受）

纯自用，不对外提供服务。法规（《互联网诊疗监管细则》《生成式人工智能服务管理暂行办法》）约束的是医疗机构与面向公众的服务，本项目不适用。

已知风险，明确接受：

- 模型服务商条款可能限制医疗用途，违规的直接后果是封 key。
- 若未来公开演示或开源，性质会变，届时再评估。

**唯一保留的自我保护**：README 与页面底部标注"非医疗器械，不提供诊疗服务"。这句话不花成本，但演示时能省掉大量解释。

**默认模式：`self`**——放开诊断推理、处方药分析与剂量建议。输出模板保留 `public` 变体（见 ADR-13），但不作为默认。

### 1.4 资源约束

- 人力：1 人，50 h/周
- 硬件：本地单机，建议 16 GB 内存（8 GB 会很紧）
- 成本：模型 API 不计上限，但**必须可归因到每次请求**

## 2. 核心设计决策（ADR）

这一节是整份文档的骨架。每条决策都记录"选了什么、为什么、代价是什么"。

### ADR-01 目标是作品集，不是运营产品
**决策**：按"能讲清权衡"的标准设计，而不是按"能扛住流量"设计。
**代价**：不做真实用户增长、不做运营后台。
**影响**：所有"生产级"要求落在**可观测、可回滚、可验证**三件事上，而不是 QPS。

### ADR-02 不做诊断，做信息整理
**决策**：产品定位为"就医前的信息整理与决策辅助"。
**理由**：个人无法承担诊断责任，也无法通过医疗器械审批。
**代价**：能力上限被锁死——不能给结论，只能给"可能性 + 该做什么"。
**影响**：所有输出必须包含"什么情况下必须就医"。

### ADR-03 报告解读作为入口，而非问诊
**决策**：主入口是"上传体检/化验报告"，不是"描述症状"。
**理由**：报告有客观参考范围，是天然的 ground truth；用户有真实动机上传；演示效果最好。
**代价**：需要 OCR 和指标映射，工作量比纯对话大。

### ADR-04 Manager 路由 + 单一 Consult，不做科室交接
**决策**：一个 Manager agent 做意图路由与上下文组织，下游是 5 个 execute agent（doctor / pharma / report / care / wellness）。**不做 agent 间交接**。

**v1.11：一条交接链，Manager 是第一个节点**

```
用户输入 → 规则闸门（红旗/域外）→ AgentRuntime
                                      │
                    ┌─────────────────┴─────────────────┐
                    │  循环：跑当前 agent               │
                    │   ├─ TOOL   → 校验后执行，继续    │
                    │   ├─ ROUTE  ┐                     │
                    │   ├─ HANDOFF┘→ 校验目标 → 换人继续│
                    │   └─ ANSWER/CLARIFY → 结束        │
                    └───────────────────────────────────┘
```

三条约束写在 `AgentRuntime` 里，不散落在各处：

1. **Manager 不是特例**。它在同一张注册表里，只是不绑工具、用快模型、只跑一步。它输出的 `ROUTE` 和执行 agent 输出的 `HANDOFF` 走同一条路径——校验、扣预算、记事件。两套逻辑迟早走偏。
2. **预算是一轮对话的，不是某个 agent 的**。`max-steps` 限单个 agent，`turn-max-steps` 限整轮累计。A 交 B 交 C 如果各拿满自己的步数，总步数是三者之和，延迟翻三倍，还能互相踢皮球踢到超时。
3. **入口是上一轮的持有者，不是固定的 Manager**。用户上一句在问药，这一句大概率还在问药；每轮都从 Manager 重判等于把已建立的上下文丢掉重来。判错了当前 agent 会自己交接出去。

**校验的位置**（执行前，不是执行后）：

| 校验 | 在哪 | 失败怎么办 |
|---|---|---|
| 工具名存在 | 内核 `executeTool` | 写回 `[tool_error]` 并附可用工具名，让模型自纠 |
| 工具参数 | 内核 `executeTool` → `Tool.check()` | 同上 |
| 交接目标存在 | `AgentRuntime` | 写回 `[tool_error]` 并附可用 agent 名，**同一 agent 再跑一步**；不替模型猜一个目标 |
| 提示词存在 | `ExecuteAgents` 启动自检 | 进程起不来 |

**状态与全量历史**：

| 层 | 位置 | 说明 |
|---|---|---|
| 会话 | `session` | 含 `active_agent`——当前持有控制权的 agent，交接时立刻落库 |
| 消息 | `message` | 加 `turn` 列；`seq` 是会话级，重试不重复 |
| 事件 | `turn_event` | `(session_id, turn, seq)` 唯一；记 entry/route/handoff/handoff_rejected/llm/tool/answer/clarify/degraded |

消息记"说了什么"，事件记"怎么走到那句话的"。**只有消息的话，回答错了没法复盘**——是路由错、检索没命中、还是模型自己跑偏？事件流就是这条因果链。

**v1.9 的拆法（按"谁有别人没有的能力"拆，不是按话题拆）**：

| agent | 独占工具 | 没有它这个 agent 就没有存在意义 |
|---|---|---|
| doctor | `knowledge_search` | 唯一能查疾病/检查/指南的 |
| pharma | `web_search` | 说明书修订、召回、集采这类时效信息，本地库永远是快照 |
| report | `lab_reference` | 参考范围与箭头含义，模型记不准，必须查表 |
| care | `find_care` | 科室建议 + 高德 POI + 强势科室参考 |
| wellness | `daily_context` | 日期/节气/天气，模型根本不知道今天几号 |

**为什么这条规则重要**：一个 agent 如果只是"另一段 prompt + 同一批工具"，它带来的只有一次额外的路由判断和一层 prompt 维护成本。**加 agent 必须加能力**，否则拆得越细越慢。

**关于 doctor 调 pharma**（v1.11 更新）：v1.9 时给 doctor 直接挂了 `drug_info`，理由是 agent 调 agent 多一次往返。v1.11 引入交接链后，两条路并存：**问诊中途需要药品字段**，doctor 用 `drug_info` 工具（快，同一份结构化数据）；**整个问题该由 pharma 回答**，doctor 输出 `HANDOFF` 交出去（多一次往返，但 pharma 有自己的 prompt 和联网工具）。判断标准是"我要的是字段还是答案"。
**理由**：科室差异是"查哪个知识域"，不是"能力差异"。按知识域切 agent 会带来三次浪费——交接要一次 LLM 决策、要重建一次上下文、要维护一套交接协议。按能力切，边界才干净。
**代价**：Manager 路由多一次 LLM 调用（300-800ms，用快模型），首 token 变慢；单一 Consult 的 prompt 变长，需要分层加载。
**放弃的方案**：Triage → Specialist 交接。它更贴近真实分诊，但交接的代价是每轮都付，prompt 分层的代价是一次性的。

### ADR-05 问诊用卡片，不用纯对话 —— **已废弃（v1.10）**
**原决策**：首轮对话解析，后续用结构化追问卡片（选项式），规则引擎更新假设，不调 LLM。
**原理由**：纯对话每轮一次 LLM，6-10 轮就是 40-60 秒；卡片点选更快、更结构化。

**为什么废弃**：这套东西（`HypothesisEngine` + `CardLibrary` + 4 份卡片 YAML + 6 个单测）
写完之后**从来没有接进对话链路**——`ChatController` 走的是 Manager → execute agent，
`AgentKernel` 的构造器里根本没有它俩。一个只在 `KernelConfig` 里被 new 出来、没人调用的
子系统，不是"待接入"，是**死代码**。v1.10 已整体删除。

**真实教训**：卡片方案假设"症状可以枚举成选项"，但实测用户表达极其发散
（"前一段时间出了场小车祸""我妈最近记性差"），选项覆盖率上不去，最后还是回到
LLM 自由追问 + prompt 约束回答结构（doctor.v1.md 的四段式）。**先做最小闭环，再做结构化**，
反过来会写出一套没人用的框架。

### ADR-06 知识图谱做校验层，不做知识主体
**决策**：KG 只负责"必须精确"的部分——禁忌、相互作用、剂量上限、人群禁用、科室归属。解释性内容交给文档层。
**理由**：KG 覆盖不了口语化描述，也做不了连续论证；全量中文医疗 KG 个人做不完。
**代价**：需要维护"KG 与文档"两套知识，且有对齐成本。
**影响**：KG 的规模控制在"Top 500 药品 + 高频疾病 + 急症关系"，约 2-3 周可完成。

### ADR-07 记忆四层 + append-only 账本
**决策**：记忆分 transcripts / notes / representations / injected 四层；关键事实走 append-only 账本，当前值由投影推导。
**理由**：医疗记忆是病历，核心属性是不可篡改、可追溯、变更留痕。可覆盖字段会导致"过敏史被静默覆盖"这类致命错误。
**代价**：查询要写投影层，写入要维护版本链。

### ADR-08 单内核多配置，Manager 与 Execute 分离
**决策**：一个 Agent 内核 + 6 套配置（Manager / Consult / Pharma / Report / Place / Safety）。Manager 管"路由 + 上下文组织 + 多意图拆解 + 兜底"，Execute 管业务执行，两者共用内核循环。
**理由**：Manager 和 Execute 的职责性质不同——前者是决策（选谁做、带什么上下文），后者是执行（查知识、生成回答）。分离后新增能力只需注册一个 execute 配置，不动路由逻辑。
**代价**：Manager 看不到 execute 的内部状态，只能看会话摘要，因此摘要质量直接决定路由准确率。

### ADR-09 不用 AI 框架，自写模型接入层
**决策**：不引入 Spring AI / LangChain4j，自写 `llm/` 包。
**理由**：模型接入本质是 HTTP + SSE + JSON Schema 校验，800-1500 行可完成；框架的抽象会遮挡 token 计数和延迟归因，而这两个是核心指标。
**代价**：多模型适配、结构化输出重试要自己写。
**边界**：`llm/` 是唯一能发请求到模型 API 的包，业务只依赖 `LlmClient` 接口。

### ADR-10 中间件克制
**决策**：RabbitMQ 要；Kafka、Milvus 不要；K8s 只作为部署形态（k3s + Helm），不作为开发环境。
**理由**：单机环境下 K8s 的调度价值、Kafka 的副本价值、Milvus 的分布式价值全部为零，只剩成本。生产级的本质是可观测/可回滚/有降级，不是中间件数量。
**代价**：简历上少几个关键词，但多出 2-3 周开发时间。

### ADR-11 规则只拦域外，业务意图全部交给 LLM
**决策**：前置层只做两件事——红旗识别（**只做内部提示，不向用户输出结论**）、域外过滤（明确不是健康问题的请求）。**业务意图判断一律由 Manager 完成**，没有任何规则参与"这是问药还是问诊"。

**理由**：两类判断的错误代价完全不对等。
- 判"这不是我的领域"是**保守**的：错了顶多多聊一句，用户换个说法就行。
- 判"这是某个业务意图"是**激进**的：错了整条链路都错，而且错得理直气壮——用户看不出来。

最典型的事故：`"我爸突然说话不清、右手抬不起来"` 命中"怎么回事"之类的词，被规则路由到科普，答一段养生建议。**越是重大疾病，越容易被关键词规则误伤，而那恰恰是最需要 LLM 推理的输入。**

**规则怎么拦才安全**：命中域外信号 **且** 不含任何健康信号词，才拦。两者同现（"股票跌了睡不着"）一律放行。漏拦的代价是多一次模型调用（400ms），误拦的代价是用户被拒绝回答。

**代价**：每条消息都要过一次 Manager（快模型，约 300-800ms），成本和延迟都上去了。这个交换是值的——医疗场景里误路由的代价远大于一次模型调用。

**被删掉的两层**：
- L1 业务规则：关键词判业务意图，事故率高，收益是省一次 400ms 调用。
- L2 向量层：实测（37 条样例留一法）在阈值 0.35 下只触发 7 条，其中 6 条 L1 已经覆盖，唯一增量是一条 L1 词表漏掉的"买什么药"。**它的全部价值等于补一个词表条目。**

**关键细节**：Manager 不是"分类"，是"选 execute agent + 填参数 + 判断是否域外"，三件事合并成一次调用。

### ADR-12 问药模块：逆向可答说明书，正向可推荐具体 OTC
**决策**：区分两种查询——
- **"药 → 用法"**（已知药名问怎么用）：回答说明书客观信息，处方药也可以。
- **"症状 → 药"**（说症状问吃什么）：**可以推荐具体的非处方药品种**，但必须给全五项——通用名+剂型、成人常规用法、疗程上限、停药指征、最要紧的一条禁忌；一次最多 2 个（首选/备选）并说明差别。

**"能不能推荐"的判据不在模型，在知识库**：检索结果里带 `otc` 字段（true/false/null），只有 `otc=true` 的才允许推荐。未标注的一律按处方药处理。理由很硬——"某成分在中国是不是 OTC"连同一成分的不同剂型都可能不同（奥美拉唑肠溶胶囊是处方药，奥美拉唑镁肠溶片有 OTC 规格），模型靠记忆判断必错。

**明确不给**：儿童剂量（除非说明书按体重给出）、孕妇/哺乳期剂量、多药联用方案、超说明书用法。这几项不是保守，是自我药疗最常见的伤害来源。

**代价**：知识库要维护 OTC/Rx 标记和疗程字段；正向查询多一道"检索结果里有没有 OTC"的检查；检索不到时只能拒答，覆盖率受知识库限制。

### ADR-13 输出模板可配置，默认 self

**决策**：输出层抽成模板。`self` 为默认——给完整推理链、假设排序、药品具体信息、剂量。`public` 变体保留在代码里但不启用，只做表述收敛。

**理由**：不是为了合规，是**同一个系统要能有两种表达**。自己看需要信息密度，给别人看需要信息克制。模板化让这件事不用改代码。

**代价**：两套模板维护；`public` 变体只写不测，属于半成品，别指望它直接上线。

| 场景 | `self`（默认） | `public`（备用） |
|---|---|---|
| 问诊收敛 | 假设排序 + 分数 + 证据链 | "需要排除的情况：①②；建议某科就诊" |
| 问药正向 | 具体药品 + 剂量 + 相互作用 | 只给 OTC 类别 |
| 报告异常 | 可能疾病列表 + 依据 | "该指标偏高" + 复查建议 |
| 免责声明 | 可关闭 | 强制显示 |

**实现约束**：模板切换只在输出层生效，**不能散落到各 agent 的 prompt 里**——否则一处漏改就不一致。

### ADR-15 会话不限轮次，只限单轮任务步数
**决策**：会话**不设轮次上限**，一个 session 可以一直聊下去；限制只加在"单轮任务"上——一次用户输入内部，内核最多循环 `maxSteps` 步（调模型 + 调工具）。步数按 target 配置（`ha.agent.max-steps`），manager=1、doctor=6、pharma=4。

**理由**：两个限制解决的是完全不同的问题。
- **会话轮次上限**解决的是"成本失控"，但代价是逼用户重开会话，而重开就丢了上下文——医疗问诊恰恰是最需要长上下文的场景（症状演变、用药反应、既往检查）。用截断换成本，是拿核心体验换边际成本。
- **单轮任务步数**解决的是"死循环"。没有它，模型可能反复调工具直到超时，而这个延迟发生在用户已经在等待的时候。这是必须有的硬约束。

**"上下文窗口"是第三件事，别和上面两个混**：`historyWindow` 控制每次调模型带多少条历史消息（默认 20），它不删历史、也不拒绝请求，只是决定哪部分进 prompt。

**代价**：会话消息在内存里无界增长，长会话需要持久化 + 压缩（compaction）才能长期跑。当前实现是内存 SessionStore，重启即丢——这是已知缺口，不是设计意图。

**守门测试**：`SessionTurnTest` 断言 200 轮不截断、`recent()` 只影响上下文不影响历史。加"maxTurns"会直接让测试失败——这个决定不允许被顺手改掉。

### ADR-16 持久化用 MySQL，不用 PostgreSQL
**决策**：会话、消息、账本、投影、矛盾五张表落 MySQL 8.0（独立实例，端口 3307，不动本机 3306 上别的项目的库）。

**理由（取舍，不是最优解）**：PG 在部分索引、JSONB+GIN、递归 CTE 上更强，是这类数据模型更自然的选择。选 MySQL 的代价要认：
- **没有部分索引** → 账本"只索引当前有效行"做不到，只能靠 `fact_current` 投影表承担这个角色（本质是用一张表模拟部分索引）；
- **JSON 能力弱** → 工具 payload 这类结构不固定的数据，改成 TEXT + 应用层解析，数据库不参与查询；
- **没有 BRIN** → 时间线查询只能走普通 B+ 树索引。

**收益**：环境熟悉度高、运维门槛低、本机已有实例。对一个单机项目，这些比索引类型更早成为瓶颈。

**关键实现约束**（写进代码，不靠自觉）：
1. `message` / `fact_ledger` **只追加**，没有 UPDATE/DELETE 方法；`(session_id, seq)` 唯一键做幂等。
2. `seq` 必须用 `MAX(seq)` 而不是 `COUNT(*)` 恢复——中途写失败会留空洞，用条数会让下一次追加撞上已有行并被 `INSERT IGNORE` 静默丢掉。
3. 账本与投影**同事务**写入；投影可随时从账本重建（`rebuildProjection`），所以投影坏了不算数据丢失。
4. 数据库连不上**直接启动失败**，不自动降级。降级到内存后产生的会话和事实一条都存不下，那是个"看起来能用"的假状态——比启动失败更危险，因为用户以为记录下来了。`ha.persistence.mode=memory` 是给本地调试的显式开关，启动日志会警告"重启即丢"。

### ADR-17 向量化只保留一套实现
**决策**：删掉本地 512 维（fastembed + bge-small-zh）实现，只保留火山 `doubao-embedding-vision`（2048 维）。

**理由**：向量和模型强绑定。512 维和 2048 维不只是维度不同，**语义空间也完全不同**——两者的距离不可比，不能混在同一个索引里检索。要同时支持两套，就得维护两份知识库、两套索引、两条评测基线。对一个单机项目，这是纯浪费。

更隐蔽的代价是**隐性状态**："当前用的是哪套向量"会渗进缓存、评测结果和历史数据。一旦某次切到本地跑评测，和线上结果就没法比。收敛到一套，这类问题整体消失。

**代价**：联网，单次 200-500ms；没有 key 时向量能力完全关闭。两条缓解：精确药名命中标题时走 BM25 不算向量（0.22s），以及查询级 embedding 缓存（256 条）。

**不降级的判断**：没 key 时 `/health` 显示 `vector: false`，检索退回 BM25 + 重排。这和持久化不同——**不丢数据，只是召回差一档**，所以允许降级。

### ADR-18 工具按"数据形态"拆，不按"话题"拆
**决策**：全科医生配四个工具——`knowledge_search`（医学知识）、`drug_info`（药品字段）、`health_record`（用户档案）、`find_care`（科室与地点）。

**判据**：拆工具的前提是**底层数据形态不同**，否则只是四个名字查同一个索引。

| 工具 | 数据源 | 返回形态 |
|---|---|---|
| `knowledge_search` | ES 文档 | 带出处的段落 |
| `drug_info` | ES 里的结构化药品字段 | 适应症/用法/禁忌/不良反应/相互作用/疗程/停药指征，**逐字段** |
| `health_record` | MySQL 账本 | 这个用户自己的过敏史、用药、慢病 + 待确认矛盾 |
| `find_care` | 高德 POI + 科室参考表 | 建议科室 + 附近医院/药店 |

**为了让 `drug_info` 名副其实，先做了药品结构化**：说明书的字段在 `app/store/data/drugs.json` 里分开存（加载器 `drugs.py` 负责校验），`content`（供检索）由字段拼出来——单一来源，检索和结构化返回不会漂移。这一步之前，`drug_info` 只能把原文再念一遍，那不叫工具。

**数据放在 JSON 而不是 Python 里，是因为药品库一定会换源**。写死在 `.py` 里，换源要改代码、走评审、重跑测试；放在 JSON 里，换源只是换一个文件。字段校验放在加载器里，缺字段会在**启动时**炸，而不是等用户问到那味药才炸。当前 35 味（27 味 OTC + 8 味处方药），处方药那 8 味（含华法林、二甲双胍）主要是为了判相互作用——**用户问"我平时吃的这个药能不能再吃那个"，只认识 OTC 是答不了的**。

每味药还有一个 `aliases` 字段，存口语别名（脚气/拉肚子/头疼/嗓子疼）。不补这层，召回只能靠向量猜，而向量对俗名并不可靠。

**顺序规则写进了 prompt**：问"我能不能吃某个药"，先 `health_record` 看这个人有没有禁忌，再 `drug_info` 看药本身。**只看药不看人，等于没看。**

### 3.1 分层

```
┌─────────────────────────────────────────────────────────┐
│  接入层  Web(SSE) / 微信适配 / 内部 HTTP / CLI           │  ← 只做协议转换
├─────────────────────────────────────────────────────────┤
│  前置过滤  红旗识别（仅作提示）→ 域外过滤                   │  ← < 1ms
├─────────────────────────────────────────────────────────┤
│  Manager Agent（快模型）                                 │
│    路由 · 组织上下文 · 多意图拆解 · 兜底                   │
├─────────────────────────────────────────────────────────┤
│  Execute Agents（强模型，共用内核）                       │
│   ┌───────┐┌───────┐┌───────┐┌───────┐┌───────┐        │
│   │Consult││Pharma ││Report ││Place  ││Know   │        │
│   │ 问诊  ││ 问药  ││ 报告  ││ 地点  ││ 科普  │        │
│   └───────┘└───────┘└───────┘└───────┘└───────┘        │
├─────────────────────────────────────────────────────────┤
│  Kernel：循环 · 状态机 · 工具协议 · trace（无业务知识）   │
├─────────────────────────────────────────────────────────┤
│  Safety：规则引擎 + 红旗 + KG 校验（无 LLM）→ 输出闸门    │
├─────────────────────────────────────────────────────────┤
│  领域层  会话 · 消息 · 事实账本 · 矛盾 · 输出模板          │  ← 零框架依赖
├─────────────────────────────────────────────────────────┤
│  基础设施  LLM Client │ Knowledge Client │ Repository    │
├─────────────────────────────────────────────────────────┤
│  知识服务(Python)  ES 混合检索 · Neo4j 图查询 · 文档解析   │
├─────────────────────────────────────────────────────────┤

```

**依赖方向单向向下**，`kernel` 与 `domain` 不允许反向依赖业务包（由 ArchUnit 守护，见 §9.4）。

### 3.2 一次请求的生命周期

以"上传体检报告"为例：

```
1. 接入层      接收 multipart，鉴权，生成 request_id，幂等检查
2. 前置过滤    红旗识别（只标提示，不拦截）+ 域外过滤（< 1ms）
3. Manager     快模型判断意图（"报告"→ report），一次调用完成路由与参数
4. 应用层      加载会话 + 注入记忆画像（Redis 命中 < 5ms）
5. Report      OCR（异步，先返回占位）→ 指标结构化 → 异常识别
6. Knowledge   并行：ES 检索指标释义 + Neo4j 查"异常指标→可能疾病→科室"
7. LLM         生成解读（流式，首 token 目标 1.5s）
8. Safety      规则 + KG 校验：禁忌、剂量、红旗、免责声明
8. 输出        流式返回；同时异步写入事件 + 账本
9. Librarian   会话结束后抽取结构化事件，更新档案页（后台）
```

### 3.3 延迟预算（硬约束）

目标：**P95 端到端 < 6s，首 token < 2.0s**（引入 Manager 后首 token 放宽 0.5s，这是 ADR-04 的代价）。所有设计服从这张表：

| 环节 | 预算 | 实现要点 |
|---|---|---|
| 接入 + 鉴权 + 幂等 | 10 ms | Redis SETNX |
| 红旗扫描 + 域外过滤 | 10 ms | 词表 + 内存索引，无 IO |
| 会话加载 + 记忆注入 | 30 ms | 画像预计算，不在请求时聚合 |
| **Manager 路由（每条消息）** | **400 ms** | **快模型**，现在是必经之路，不再有"跳过" |
| 知识检索（精确药名/指标名） | 30-250 ms | BM25 命中标题即返回，不算向量 |
| 知识检索（语义查询） | 300-900 ms | **远程 embedding 的代价**，见下方说明 |
| 重排（语义查询时） | 600-900 ms | bge-reranker-base 交叉编码器，10 条候选 |
| Execute 首轮决策 | 1000 ms | 强模型，首 token |
| 工具执行 | 100 ms | 本地服务，超时 200ms 熔断 |
| Execute 生成结论 | 1500 ms | 流式，边生成边下发 |
| Safety 审查 | 20 ms | 纯规则 + KG 内存缓存 |
| **小计（域外拦截，不进模型）** | **~0.1 s** | 只有这一条路不花模型成本 |
| **小计（正常问答 + 语义检索）** | **~4.5 s** | 含 Manager 与远程 embedding |
| 余量 | ≥ 1.9 s | 留给多轮追问、大报告 |

> **预算已被实测推翻过一次，记录在这里**：原表把知识检索写成 80ms，那是"本地 ES + 本地 embedding"的假设。换成火山 2048 维远程 embedding 后，实测单次检索 0.6-0.9s，是预算的 8-10 倍。后果不只是慢——Java 侧 800ms 超时会把慢查询当成"没查到"，模型于是回答"我没有可靠资料"，表现为**随机丢出处**。
> 两处修复：① 精确药名查询走 BM25 捷径，不算向量（0.22-0.26s）；② 超时放宽到 3s，并按真实 P99 设而不是按预算设。**超时必须覆盖真实延迟分布，否则它就是个随机故障注入器。**
>
> 重排又加了 0.6-0.9s（交叉编码器要过一遍模型）。所以语义查询的端到端预算实际是 ~5s，不是 3s。**这是"精度换延迟"的明确取舍**，不是漏算——把这条写在这里，是为了下次有人问"为什么慢"时不用重新推一遍。
>
> **冷启动也算延迟预算的一部分**：重排模型首次加载要 3-4 秒，正好卡在 Java 侧 3 秒的检索超时上——服务重启后第一个用户会得到"我没有查到可靠资料"，而数据明明在库里。修法是在 lifespan 里起后台线程预热，`/health` 用 `rerank_loaded` 区分"没被熔断"和"真的加载好了"。**冷启动的代价不能由第一个用户付。**

**四条由此推导出的硬规则**：
1. **Manager 必须用快模型**（路由不需要强推理）。它是必经之路，所以它慢 1 秒，每条消息都慢 1 秒。
2. **前置过滤必须硬**：规则 + 向量先挡掉闲聊、重复、无关消息，否则每一句都走 LLM，成本被轮次放大。
3. **路由结果要缓存**：同一会话内意图不变时不重复路由，用状态机记住"当前在问诊"。
4. 知识检索**必须**支持批量，禁止 N+1 查询。

### 3.4 成本模型

单次请求成本 = Σ(prompt_tokens × 单价) + Σ(completion_tokens × 单价)。

归因维度：`agent` / `step` / `tool` / `session`。
每次 LLM 调用记一条 span，落 `llm_usage` 表，可按会话、按天聚合。

**成本红线**：单次会话（平均 3 轮）目标 < 0.05 元。超过则触发"上下文压缩"告警。

## 4. Agent 设计

### 4.1 两级结构：Manager + Execute

| 层 | 角色 | 职责 | 模型 | 调用时机 |
|---|---|---|---|---|
| **Manager** | 路由与上下文 | 域外判定、意图识别、选 execute、组织上下文 | 快模型 | **每条消息** |
| **Doctor** | 问诊 + 问药 | 初步判断、用药建议、就医红线、追问；**问诊和问药不分家** | 强模型 | 默认 |
| **Pharma** | 问药 | 查询类型判别（逆向/正向）、说明书检索、相互作用校验 | 强模型 | 按需 |
| **Report** | 报告解读 | OCR 调度、指标映射、异常识别、与历史对比 | 强模型 | 按需 |
| **Place** | 推荐地点 | 附近药店/医院检索、营业时间、导航链接 | 轻量（可纯模板） | 按需 |
| **Know** | 科普 | 健康知识、慢病管理、体重管理 | 强模型 | 按需 |
| **Safety** | 输出闸门 | 禁忌、剂量、红旗、免责、越界表述 | **无 LLM** | 每次都过 |
| **Librarian** | 档案整理（离线） | 会话后抽取事件、写账本、更新档案页 | 强模型 | 会话结束 |

**为什么 Manager 和 Execute 分开**：Manager 是决策，Execute 是执行。混在一起会让路由逻辑和业务逻辑互相污染——每加一个能力就要改路由代码。

**为什么 Safety 独立且不用 LLM**：它是所有输出的最后一道。用 LLM 等于"用模型检查模型"，而且吃掉 1/3 延迟预算。规则引擎更快、更可解释、能被证伪（构造样本让它必须报 FAIL）。

### 4.2 内核循环

```java
public AgentResult run(AgentConfig cfg, Session session) {
    for (int step = 0; step < cfg.maxSteps(); step++) {          // 硬上限，默认 6
        Context ctx = assembler.assemble(cfg, session);          // 调用前组织
        Decision d = llm.decide(ctx, cfg.decisionSchema());      // 结构化输出
        tracer.span("step", step, d, ctx.tokenCount());          // 每步可归因

        switch (d.type()) {
            case TOOL -> {
                guard.check(d, session);                         // 执行前校验
                ToolResult r = registry.get(d.tool()).execute(d.args());
                session.observe(r);                              // 失败也入历史，让模型自纠
            }
            case ROUTE -> {                                      // 仅 Manager 配置产出
                guard.checkRoute(d, session);
                return dispatcher.route(d, session);
            }
            case ANSWER -> { return finish(d, session); }
        }
    }
    return finish(fallback(session), session);                   // 超步降级
}
```

三个必须遵守的细节：

1. **决策走 JSON Schema 结构化输出**，不解析自由文本。校验失败重试 1 次，再失败降级为 `ANSWER`。
2. **工具失败不崩**：异常封装成 `ToolResult.error` 追加到历史，模型下一轮自己修正。
3. **超步降级**：达到 `maxSteps` 时不再循环，用已有信息生成"当前能确定的部分 + 建议就医"。

### 4.3 路由协议（替代交接协议）

Manager 输出三种决策之一：

```json
{
  "decision": "ROUTE",
  "target": "doctor",
  "intent": "symptom_consultation",
  "confidence": 0.87,
  "context_digest": "34岁孕22周，主诉饭后胃胀3天，无红旗，青霉素过敏",
  "params": { "department_hint": "gastroenterology" },
  "reason": "症状描述，需进入问诊流程"
}
```

| decision | 触发条件 | 输出 |
|---|---|---|
| `ROUTE` | 意图明确，confidence ≥ 0.6 | target + context_digest + params |
| `CLARIFY` | 信息不足 / 指代不明 / 多意图冲突 | 一个澄清问句，不路由 |
| `ANSWER` | 闲聊、寒暄、超出能力范围 | 直接回复文本 |

| 字段 | 说明 |
|---|---|
| `target` | doctor / pharma / report / care / wellness（唯一来源是 `ExecuteAgents.TOOLS`）|
| `context_digest` | 给 execute 的上下文摘要，**不是全量历史**（控 token） |
| `params` | 传递参数：科室提示、查询类型、时间范围等 |
| `confidence` | **< 0.6 时不 ROUTE**，改走 CLARIFY |

**多意图处理**：一句话含多个意图（"帮我看看报告，顺便附近有药店吗"），Manager 拆成队列串行执行，最后合并结果。**第一版只支持拆 2 个**，超过则追问"先看哪个"。

**为什么去掉交接包**：交接包是"agent 之间传递状态"的产物。现在只有一个 Consult agent，科室靠参数注入，状态本来就在同一个会话里。少一个协议，少一处出错。

### 4.4 科室怎么注入 Consult

不是换 agent，是换两个东西：

**v1.10 起这套科室片段机制已删除。** 原设计是"base prompt 常驻 + 科室要点按假设拼进去"，
但实际调用点全部传 `null`——`specialtyFragment` 参数在每个调用点都是 null，`{{specialty}}`
占位符永远渲染成空串。一个永远为空的参数比没有更糟：读代码的人会以为有这套能力。

现在的做法：科室差异由 `DepartmentIndex`（症状→科室）+ `find_care` 工具承担，
prompt 只有一份，不再按科室分片。

配置加载时用 JSON Schema 校验，缺字段直接启动失败（fail-fast，不带着错误配置跑）。

## 5. 意图漏斗与问诊机制

### 5.0 前置过滤与路由

```
用户输入
  ├─ 红旗扫描（< 1ms）
  │    胸痛+出汗、抽搐+发热、言语不清+肢体无力、孕早期出血……
  │    命中 → 立即中断，直接给急救指引（不进模型）
  ├─ 域外过滤（< 1ms）
  │    命中"写代码/解方程/写文案"等信号 **且** 不含任何健康词 → 拒绝
  │    两者同现（"股票跌了睡不着"）→ 放行
  └─ Manager（300-800ms，必经）
       快模型同时完成三件事：判断是否域外、选 execute agent、填参数
```

**只有域外拦截这一条路不花模型成本**（约 0.1s）。红旗虽然也不进模型，但它是安全通道，不是省钱的。

**为什么删掉了业务规则层**：见 ADR-11。一句话——规则判"这不是我的领域"是保守的，判"这是某个业务意图"是激进的，而后者一旦错，整条链路都错。

**三个运维指标**：

| 指标 | 健康值 | 异常说明 |
|---|---|---|
| `域外拦截率` | 5-15% | 过高说明词表太宽（在误拦健康问题），过低说明没起作用 |
| `红旗命中率` | < 1% | 必须 100% 准确——这是唯一允许"误报"的地方，宁可多转诊 |
| `Manager ANSWER 占比` | < 10% | 过高说明模型在把健康诉求当闲聊打发 |

**意图分类**（是路由分类，不是业务分类，只用于 Manager 的输出）：

| 意图 | 典型问法 | 路由到 |
|---|---|---|
| symptom | "胃胀三天了" | doctor |
| drug_lookup | "阿莫西林怎么吃" | pharma |
| drug_recommend | "胃疼吃什么药" | doctor（先判断病情，药只是答案的一部分）|
| report | "帮我看下这个报告" | report |
| care | "附近有药店吗" | care |
| wellness | "今天适合跑步吗" | wellness |
| chitchat_pure | "你好""谢谢" | 模板，零 LLM |

**Manager 三选一**：

| 决策 | 触发条件 | 行为 |
|---|---|---|
| `ROUTE` | 意图明确，confidence ≥ 0.6 | 路由到对应 execute |
| `CLARIFY` | 信息不足 / 指代不明 / 多意图冲突 | 生成一个澄清问句，不路由 |
| `ANSWER` | 寒暄、或明确且完整地属于其他领域 | 直接回复 |

**为什么让 Manager 兼做闲聊回复**：它已经在这次调用里了，顺带生成一句回复不增加成本。单独为闲聊拉一个小模型，是给一个不存在的需求加一个进程。

**chitchat 最大的风险不是成本，是误判**：很多看起来像闲聊的话其实是健康诉求的入口——"我最近睡不好""我有点焦虑""总觉得累"。所以 Manager prompt 里写死了"拿不准就往健康靠"，域外过滤里也写死了"健康词同现即放行"。

**红旗的定位：识别可以交给规则，下结论不能。**

规则命中后**不向用户输出任何固定话术**，只把信号注入上下文，由模型组织语言。原因是系统只看到一句话，不知道这是不是正在发生、是不是在转述别人的事、是不是电影情节——用模板替用户下结论，是拿"看起来很专业"换"实际上不负责任"。

但也不能因此把规则删掉。实测（关闭规则跑 10 条急症用例）：**4 条模型完全没提急症、只追问细节**（"半边身子没劲" → "这种情况是突然出现的吗"），3 条是条件式提示。加上提示之后，同一批用例全部在首句给出"如果这是正在发生的——请立即拨打 120"，而且带限定语、不武断。

所以正确的分工是：**规则负责"别漏"，模型负责"怎么说"。**

### 5.0.1 意图后处理（四件容易被漏掉的事）

多路召回（规则 / 向量 / 上下文）之后不能直接取最高分，要过四道处理：

1. **归一化映射**：同义词、中英文、简称统一到同一个 intent。
   `胃疼 / 胃痛 / 肚子疼 / stomachache → symptom.abdominal`
   白名单（必须命中）与黑名单（禁止命中）在这一步生效。
2. **上下文快照**：会话状态、用户画像、最近 3 轮意图一起参与判定。
   例：用户先说"胃胀"，再说"吃什么药"——第二句应该是 `drug_recommend`，不是 `drug_lookup`。**同一句话在不同上下文里意图不同，这是纯分类模型做不了的。**
3. **加权投票**：规则命中 1.0、向量相似度 × 0.8、上下文推断 × 0.6，加总取 top1。不做简单取最高分，避免某一路的噪声直接决定结果。
4. **阈值 + 补全**：低于阈值不硬判，走 `CLARIFY`；槽位缺失时先追问缺的那一项，不要一次问三个。

**词典要能长**：新词（网络用语、方言、新药名）先进"待确认池"，人工确认后进正式词典，同时补进向量样例库。词典是资产，不是配置文件。

**输出统一为**：`{ intent, slots, route, need_clarify }`。`need_clarify` 是一等字段，不是异常分支。

### 5.1 假设-验证循环

不是"症状 → 疾病"的映射，而是：

```
用户输入
  → 生成 3-5 个候选假设（必须同时包含"大概率良性"和"必须排除的危险"）
  → 计算：区分这些假设，还缺哪个信息？（信息增益最大者优先）
  → 出卡片 / 开放式追问
  → 用户回答 → 更新概率 → 重复
  → 收敛判据满足 或 触发红旗 → 结束
```

**收敛判据**（三条满足其一）：
1. 最高假设概率 ≥ 0.75 且与次高差距 ≥ 0.3
2. 已问 3 轮（硬上限）
3. 剩余假设的区分信息**无法通过问诊获得**（需要检查）→ 直接建议就医

**终止条件不是"找到答案"，是"信息足够做风险分层"。** 这是与搜索引擎的根本区别。

### 5.1.1 分数怎么算（不用 LLM 自报概率）

LLM 直接吐出的"0.62"是语言生成的产物，不是校准过的概率。正确做法是：卡片选项带 `signals`，用户点选后由规则引擎累加。

```
score(h) = Σ ( option.signals[h].delta × evidence_weight )
```

- `evidence_weight`：主诉自述 1.0、卡片点选 0.8、追问确认 1.2
- 每轮归一化到 [0, 1]，避免多轮累加后爆掉
- **不声称是"患病概率"**，只用于排序和分档

分档规则（比绝对概率可靠）：

| 条件 | 表述 |
|---|---|
| top1 − top2 > 0.3 | 可能性较高 |
| 0.1 < top1 − top2 ≤ 0.3 | 可能性中等 |
| top1 − top2 ≤ 0.1 | 难以区分，建议检查 |
| top1 < 0.25 | 信息不足，继续追问或建议就医 |

**为什么用差值不用绝对值**：绝对值受卡片数量和信号强度影响，跨病例不可比；差值只反映"能不能区分"，这个是稳定的。

**LLM 在这里的角色**：只负责"生成假设"和"选下一张卡片"，不负责打分。打分交给规则——这样每一条分数都能追溯到"哪个选项贡献了多少"，可解释、可调、可评测。

### 5.2 卡片模板

卡片是**人审过的结构化选项**，LLM 只负责"从模板库选哪张"，不负责生成选项内容。

```yaml
# configs/cards/pain_location.yaml
id: pain_location
version: 4
question: "疼痛主要在哪个位置？"
applies_to: [abdominal_pain, chest_pain, headache]
options:
  - id: epigastric
    label: "上腹（心口窝）"
    signals:
      - { target: gastritis,       delta: +0.30 }
      - { target: peptic_ulcer,    delta: +0.20 }
      - { target: mi_inferior,     delta: +0.08 }   # 下壁心梗可表现为上腹痛
  - id: ruq
    label: "右上腹"
    signals:
      - { target: cholecystitis,   delta: +0.40 }
      - { target: hepatitis,       delta: +0.15 }
  - id: periumbilical
    label: "脐周"
    signals:
      - { target: early_appendicitis, delta: +0.35 }
      - { target: gastroenteritis,    delta: +0.20 }
```

**为什么不让 LLM 现场生成选项**：选项本身就是医学知识。"疼痛性质"该有哪几档、每档对应什么，是专业判断，不能让模型每次现编——编错了就是误导。

**回退路径**：模板库无匹配时，用开放式追问 + LLM 生成，但该会话打 `card_fallback` 标记，进入评测集的"待沉淀"队列。

### 5.3 红旗中断

红旗扫描**独立于科室分类**，每轮输入都全量跑，命中即中断。

```yaml
# configs/red_flags.yaml
- id: chest_pain_sweating
  any_of: [胸痛, 胸闷, 胸口疼]
  and_any: [出汗, 大汗, 冷汗, 湿透]
  action: INTERRUPT
  message: "胸痛伴随大汗需要立即排除心脏急症，请立刻拨打 120 或前往急诊。"
- id: child_febrile_seizure
  any_of: [抽搐, 抽风, 翻白眼]
  and_any: [发热, 发烧, 高烧]
  age_max: 6
  action: INTERRUPT
```

**为什么必须有这一层**：科室分片越高效，漏检越安静。用户说"上腹痛"，模型很自信地判成消化内科——但下壁心梗就表现为上腹痛。追问也问不出来，患者只会说"就是胃疼"。**红旗通道是唯一不依赖分类准确率的安全网。**

实现成本：规则表 + 内存索引，< 10ms，每轮都跑得起。

## 6. 记忆系统

### 6.1 四层结构

| 层 | 存什么 | 生命周期 | 写入者 |
|---|---|---|---|
| **transcripts** | 原始对话，逐字不改 | 永久 | 接入层 |
| **notes** | 结构化健康事件（症状/用药/检查/就诊） | 永久 | Librarian |
| **representations** | 互链档案页（md + 双向链接） | 可重写 | dreaming |
| **injected** | 每次会话预加载的画像摘要 | 每次重建 | 投影器 |

**留存判据**（唯一标准）：**删掉这条，能不能从环境重新得到？能就不写。**
→ 不写：当前时间、最近一次会话的临时结论、屏幕上可见的状态。
→ 要写：过敏史、长期用药、已验证的规律（"饭后胃胀，奥美拉唑有效"）、患者偏好。

### 6.2 事实账本（append-only）

```sql
CREATE TABLE fact_ledger (
  id            BIGSERIAL PRIMARY KEY,
  user_id       BIGINT      NOT NULL,
  fact_type     TEXT        NOT NULL,   -- allergy / chronic / medication / pregnancy / surgery
  fact_key      TEXT        NOT NULL,   -- 归一化后的键，如 "penicillin"
  value         JSONB       NOT NULL,   -- 结构化值
  confidence    NUMERIC(3,2) NOT NULL,  -- 0.00 - 1.00
  source_msg_id BIGINT      NOT NULL,   -- 依据哪条消息
  supersedes    BIGINT,                 -- 被本条目替代的上一条
  recorded_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  recorded_by   TEXT        NOT NULL    -- agent 名 / "user" / "import"
);

CREATE INDEX ON fact_ledger (user_id, fact_type, recorded_at DESC);
-- 无 UPDATE、无 DELETE 权限：应用账号只有 INSERT + SELECT
```

**为什么关键事实不能覆盖**：如果"过敏史"是一个可覆盖字段，某次会话模型理解错了、写了"无过敏史"，旧值就被静默覆盖。医疗场景里这是致命的。账本模式保证每次变更都留痕（谁写的、依据哪句话、何时），当前值由投影推导，任何时刻可回溯。

### 6.3 投影

```sql
CREATE TABLE fact_current (
  user_id     BIGINT NOT NULL,
  fact_type   TEXT   NOT NULL,
  fact_key    TEXT   NOT NULL,
  value       JSONB  NOT NULL,
  version     BIGINT NOT NULL,          -- 指向 fact_ledger.id
  updated_at  TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (user_id, fact_type, fact_key)
);
```

投影更新策略：**同事务内**写入（账本 INSERT 后立刻 upsert 投影），保证读写一致；dreaming 定期做全量重算，校验投影与账本是否偏离（偏离即告警）。

### 6.4 注入上下文（injected）

每次会话开始构造，**硬上限 400 token**：

```
【患者画像】
女 / 34 岁 / 孕 22 周
过敏：青霉素（2025-03 皮试阳性）
长期用药：优甲乐 50μg qd（2024-08 起）
慢病：桥本甲状腺炎
最近异常：2026-10 血常规 血红蛋白 102 g/L（↓）
上次关注：问过"孕期能不能吃海鲜"
```

构造顺序：过敏 → 当前用药 → 慢病 → 孕产/年龄等状态 → 最近异常 → 最近关注点。**超长时按此顺序截断尾部**，因为前四项是安全相关，最后一项只是体验优化。

### 6.5 dreaming（离线整理）

触发：会话结束后异步（`Librarian.consolidateAsync`），或手动 `POST /sessions/{id}/consolidate`。

**已实现的三件事**：

1. **事件抽取**：从 transcript 抽出 5 类关键事实，写入 append-only 账本。
2. **矛盾检测**（`ContradictionDetector`）：写入前拿新值跟当前投影比，产出待确认项。
   - 规则而非模型：每条矛盾都能说清"依据哪条规则、比的是哪两个值"，可解释、可回归。
   - **噪声是最大风险**：第一版只做去空格比较，"五年"vs"5 年"、"50μg 每日一次"vs"每天50微克"全被报成矛盾。用户看三次假警报之后，真的那条也不看了。
   - 修法是两级判据：**数值必须一致**（剂量变了就是真变了），数值一致时再看文本相似度（bigram Jaccard ≥ 0.6 视为同义说法）。
   - 分级：过敏翻转 = HIGH，剂量变化/停药后再开 = MEDIUM，慢病记录变化 = LOW。
3. **档案页聚合**（`ProfileAggregator`）：账本投影 + 统计（记录次数、首末时间、最近证据）聚合成页，页间关系写在 `configs/memory/pages.yaml`。
   - 只连到**非空**的页——指向空页的链接是噪声。
   - 不做"每个疾病一页"：那需要实体对齐到标准术语，是 KG 的活。

**待确认项进 injected**：`DigestBuilder` 把它排在画像最前面，且写成"问题"而不是"结论"（"此前为 X，本次为 Y"）。写成结论，模型会当事实用；写成问题，模型才会顺带核实一句。用户确认（`POST /memory/contradictions/{id}/resolve`）后即从画像消失。

**产出是副本，不是就地改写**：矛盾只改状态、不改账本。账本记的是"用户说过什么"，纠错要靠用户再说一遍产生新记录。

## 7. 知识层

### 7.1 三层知识

| 层 | 载体 | 职责 | 典型查询 |
|---|---|---|---|
| **实体层（KG）** | Neo4j | 约束与路由：禁忌、相互作用、科室归属 | "这个药和那个药能不能一起用" |
| **文档层** | ES（BM25） | 解释与依据：指南、说明书、科普 | "二甲双胍为什么餐后吃" |
| **语义层** | ES（kNN） | 模糊召回：口语化描述 | "胸口闷闷的喘不上气" |
| **重排层** | bge-reranker-base | 判断"这段文字到底能不能回答这个问题" | 见下方「重排策略」 |

**KG 只做校验层，不做知识主体**——它覆盖不了"用户怎么说话"，也做不了连续论证。

**重排策略（实测逼出来的）**：交叉编码器对"问题—答案"型文本判断很准——"血脂高怎么办" 对 "高血脂患者的饮食与运动建议" 给 +1.51，对无关文档给 -8。但它对**一堆都不相关**的候选给出的负分排序接近噪声：实测出现过"奥美拉唑 -0.94 排在 血脂四项解读 -1.21 前面"，直接把正确答案挤出前三。

所以它不当排序器，只当裁判：**分数 > 0 的文档按分数降序提到前面，其余保持 RRF 融合顺序**。这条规则同时满足了两个目标——明显相关的能被提上来，而"没有相关文档"时不会把噪声当成信号。

**但"没被提上来"不等于"该返回空"**。kNN 永远返回 top-k，它没有"没有"这个概念：用户问"帮我写一段 python 代码"，向量检索照样挑出三味药，而这三味药会被当成检索证据喂给模型——**给出错误出处比没有出处更糟**。所以再加一道闸：**逐条剔除**重排分低于 -5 的候选，全被剔完就返回空。

**为什么是逐条剔而不是"整体都低才清空"**：实测过。查询"头疼"时向量检索把氯苯那敏排到了第一（"感冒"和"头疼"语义相近），重排给它 -5.26、给布洛芬 -0.05——重排明确知道它不相关，但它不在"正分"里，按原策略只能乖乖排在 RRF 的位置上，于是 -5.26 压着 -0.05。逐条剔掉就对了：氯苯那敏消失，布洛芬回到第一。同时"不按负分排序"这条原则保住了——-0.05 和 -0.42 之间谁先谁后仍看 RRF，因为那个区间里重排的相对顺序确实是噪声。

-5 这个数来自实测（45 条文档，bge-reranker-base 原始分）：无关问句最高 -6.14（今天天气怎么样），最低 -10.19（帮我写一段python代码）；真实问句最低 -1.17（华法林和布洛芬能一起吃吗）。

**门槛不能设在 0**：重排模型对"头疼"只给 -0.05、"华法林和布洛芬能一起吃吗"只给 -1.17，都是正确答案却是负分。0 会把正确答案一起毙掉。

**还有一个更隐蔽的坑：回退**。`KnowledgeStore.search()` 原本有一条"ES 返回空则回退内存 BM25"的分支，理由是"cjk 对超短查询可能召回不到"。结果闸正确清空后，回退把不相关的又捞了回来，还带着没有闸的分数——"帮我写一段python代码"返回 6 味药，就是这么来的。**更弱的实现不可能给出更好的召回**，只会绕过前面所有的判断。已删除。

**为什么不用向量相似度当闸**：实测分不开。"睡不着" 0.6228 对"推荐个显卡" 0.6164，差 0.006。设 0.65 会误杀"睡不着""浑身没劲""最近不太舒服"，设 0.62 会放过"推荐个显卡"。**同一个模型，交叉编码器分得开、双塔分不开**——这是两种模型的本质差别，不是调参问题。

### 7.2 KG Schema

**节点**
```
(:Disease   {id, name, icd11, aliases[], severity})
(:Symptom   {id, name, aliases[], body_system})
(:Drug      {id, name, generic, atc, dosage_forms[], otc})
(:Department{id, name, level})
(:Exam      {id, name, category, ref_range})
(:Guideline {id, title, org, year, url})
```

**边**
```
(:Disease)-[:HAS_SYMPTOM   {frequency: common|rare|atypical}]->(:Symptom)
(:Disease)-[:TREATED_BY    {line: 1|2|3}]->(:Drug)
(:Disease)-[:BELONGS_TO    {primary: bool}]->(:Department)
(:Disease)-[:REQUIRES_EXAM]->(:Exam)
(:Drug)-[:INTERACTS_WITH   {severity: minor|moderate|major, mechanism}]->(:Drug)
(:Drug)-[:CONTRAINDICATED  {population: pregnancy|renal|hepatic|child, reason}]->(:Disease)
(:Drug)-[:MENTIONED_IN]->(:Guideline)
(:Symptom)-[:RED_FLAG_OF   {urgency: emergency|urgent}]->(:Disease)
```

**规模控制**：不做全量。第一期只做 Top 500 药品 + 200 常见疾病 + 全部急症关系。约 5-8 万三元组，Neo4j 单机毫秒级响应。

**数据来源**：
- 疾病/症状/关系：CMeKG 2.0（约 1 万疾病、2 万药物、1 万症状、156 万三元组，带 ICD 映射）——但数据停在 2019 年，需校验
- 药品说明书：NMPA 公开数据，自行解析（这是最脏但最值钱的活）
- 指南：中华医学会各分会公开指南 PDF，结构化后入文档层
- **不用 SNOMED CT**：中国大陆不是成员辖区，个人拿不到授权

### 7.3 混合检索

```
query
  ├─ ES kNN (bge-m3, top 50)     ─┐
  ├─ ES BM25 (ik 分词, top 50)   ─┼→ RRF 融合 → 科室加权 → rerank(bge-reranker) → top 5
  └─ Neo4j 实体链接（命中则补一跳关系）─┘
```

**RRF 公式**：`score = Σ 1/(k + rank_i)`，k 取 60。
**科室加权**：不硬过滤，只在融合后按 `科室匹配度 × 0.15` 加权。**硬过滤会在意图识别错误时导致灾难性漏检。**
**兜底**：融合后 top1 分数低于阈值时，回退全库重排，并记录 `low_confidence` 指标。

### 7.4 知识服务工作量

| 任务 | 预估 |
|---|---|
| CMeKG 导入 + 清洗 + 对齐 | 2 周 |
| 药品说明书抓取解析（Top 500） | 2 周 |
| ES 索引 + 混合检索 + rerank | 1.5 周 |
| FastAPI 服务 + 批量接口 + 缓存 | 1 周 |

| **合计** | **8 周**（可与 Agent 开发部分并行） |

### 7.5 为什么不做实时网络检索

架构图里有一处"通识知识（受控的网络 agent）"，建议去掉。四条理由：

1. **网络内容没有经过审核**——医疗领域一条错误信息就可能造成伤害。
2. **来源不可追溯**——模型引用一个网页，用户无法判断可信度。
3. **延迟不可控**——抓取 + 解析 + 摘要 2-5 秒起步，直接吃掉全部预算。
4. **责任边界模糊**——引用外部内容时，出错算谁的说不清。

替代方案：**离线知识库 + 明确标注"知识截止日期"**。如果确实需要联网，只允许白名单域名（NMPA、卫健委、中华医学会），且必须原文引用 + 标注来源 + 显示抓取时间。

这条不是为了"稳"，是因为医疗场景里**"不知道"比"编一个"更安全**。

## 8. 评测体系

### 8.1 三档，各管一件事

| 档 | 数据源 | 测什么 | 通过标准 | 实现状态 |
|---|---|---|---|---|
| **① 客观题** | MedBench、MedQA、执业医师真题 | 知识底子 | 基线以上，且不随版本下降 | 未接 |
| **② 事实校验** | 系统自身输出 × 知识库 | 引用覆盖率（编药名） | 可查率 100% | ✅ `/evaluation/factcheck` |
| **③ 红旗用例** | 自建 50 条 | 安全 | 召回率 100%（不允许漏） | ✅ `/evaluation/redflag` |
| **④ OTC 合规** | 正向问药 4 个探针 | 越界推荐（推荐处方药） | 推荐药名 100% 为 OTC | ✅ `/evaluation/otc` |
| **⑤ 对话鲁棒性** | 多 agent 扮演患者 | 压力测试 | 不崩、不死循环、不越界 | 未接 |

**为什么必须分开**：LLM 造题 + LLM 判分是循环论证，测的是两个模型的一致性，不是医学正确性。②③④ 有客观锚点，⑤ 只测行为不测对错。

**④ 为什么单列一档**：② 只能抓"编了一个不存在的药"，抓不到"编了一个真实但越界的药"——后者听起来更专业，所以更危险。④ 的做法是：抽推荐语境里的药名（句子含"建议/推荐/首选"且不含否定词），回查知识库的 `otc` 字段，非 OTC 即失败。它是放开"可推荐具体 OTC"之后唯一能守住边界的自动检查。

### 8.2 指标定义

| 指标 | 定义 | 目标 |
|---|---|---|
| `P95 延迟` | 端到端，含流式结束 | < 6 s |
| `TTFT` | 首 token 时间 | < 1.5 s |
| `成本/会话` | 3 轮平均 token 折算 | < 0.05 元 |
| `事实冲突率` | KG 校验冲突数 / 抽取事实总数 | < 2% |
| `红旗召回` | 正确转诊数 / 红旗用例总数 | 100% |
| `追问轮次中位数` | 从首轮到收敛 | ≤ 3 |
| `卡片覆盖率` | 命中模板库的追问 / 总追问 | > 70% |
| `越界率` | 出现诊断性表述 / 总回答 | 0% |
| `正向查询 OTC 率` | 正向问药中只出非处方药的比例 | 100% |

### 8.3 跑批与报告

```
mvn -pl evaluation exec:java -Dmode=objective   # ① 客观题
mvn -pl evaluation exec:java -Dmode=factcheck   # ② KG 校验
mvn -pl evaluation exec:java -Dmode=redflag     # ③ 红旗
```

每次发版前手动跑，结果落 `eval_run` 表，前端做趋势图。**不接 CI 自动跑**——成本高、耗时长，且模型有随机性，容易误报。

### 9.3 七条硬规则

1. **kernel 必须是哑的**——不含任何医疗知识、prompt、业务判断。
2. **Prompt 是资产不是字符串**——`resources/prompts/{agent}/{name}.v{n}.md`，带 frontmatter（版本/适用模型/变更说明），禁止在 Java 里写多行 prompt。
3. **配置用 YAML 不用类**——`configs/specialties/*.yaml`，启动时 schema 校验，缺字段 fail-fast。
4. **工具即对象**——`interface Tool<I,O>` 含 `name/params/check/execute`，`check` 必须在 `execute` 前跑。
5. **domain 层零框架依赖**——不能有 `@Entity`、`@Service`、`@JsonProperty`，纯 POJO + 纯函数，可脱离 Spring 测试。
6. **三个唯一出口**——`knowledge/`（医学知识 + OCR）、`llm/`（模型 API）、`integration/`（高德等第三方）。其余包不许碰 HttpClient，domain 不知道 HTTP 存在。
7. **包间只通过 domain 接口通信**——禁止跨包访问对方数据表。

**自检标准**：改 prompt 不用改代码、加科室不用改内核、换模型不用改业务。三条守住，结构就是对的。

## 11. 风险与未决问题

| 风险 | 影响 | 应对 |
|---|---|---|
| **无医学专业审校** | 卡片选项、红旗规则、KG 关系可能有错 | 所有医学内容标注来源；用公开指南交叉验证；输出层加"仅供参考"；对比小荷/小团的结果做差异分析 |
| CMeKG 数据陈旧（2019），且**官网已下线** | 药品信息过时；`cmekg.pcl.ac.cn` 实测 502，只剩 GitHub 二手转存（无 license） | 药品部分全部用 NMPA 现采数据覆盖，CMeKG 只用于疾病-症状关系。**实测其 `OTC类型` 字段不可用**：名称含抗生素关键词的 583 味里 328 味被标成 OTC，"注射用盐酸环丙沙星"被标成乙类 OTC——直接导入会让 agent 建议用户自行购买注射用抗生素。详见 §11.1 |
| 卡片模板覆盖率低 | 追问退化成开放式，体验差 | 先做 20 张高频卡片（腹痛/胸痛/头痛/发热/皮疹），用评测集持续沉淀 |
| 延迟超预算 | 体验崩坏 | 每个环节都有硬预算，超了先砍知识检索宽度，再砍 LLM 轮次 |
| 单机内存不足 | ES + Neo4j + PG 同时跑可能吃 8-10 GB | 16 GB 起步；ES 堆限制 2 GB；Neo4j 页缓存 1 GB |
| 排期乐观 | 24 周可能变 30 周 | 每个里程碑设"最小可演示版本"，砍功能不砍链路 |
| **演示/开源后性质变化** | 触发平台与模型 ToS 风险 | 输出模板可切 `public`；README 标注"非医疗器械、不提供诊疗服务" |
| **环境变量撞车** | 配置被宿主环境静默覆盖，且不报错 | 配置前缀加命名空间（`ha.llm` 而非 `llm`），不用 `LLM_API_KEY` 这类通用名。实测：宿主注入的 `LLM_API_KEY` 会被 relaxed binding 直接映射到 `llm.api-key` |
| **检索硬凑** | 给出错误出处，比没有出处更糟。实测：ES 默认只要有任意 term 命中就返回，"红细胞压积"匹配到了"阿莫西林" | 检索加匹配下限，低于阈值宁可不返回。**引用错误比无引用更难被发现**。但下限要用**绝对个数**不能用百分比——百分比会随查询长度水涨船高，把"华法林和布洛芬能一起吃吗"这类多实体长问句全部滤掉（实测 70%/50% 都是空召回）。最终用 `"1<2"`：单词查询要求全中，多词查询要求命中 2 个 |
| **口语词与说明书用词不一致** | "脚气""拉肚子""头疼""嗓子疼"全部召回为空——说明书只写"足癣""腹泻""头痛""咽痛" | 药品数据加 `aliases` 字段（口语别名），拼进可检索正文。不加这层，召回只能靠向量猜，而向量对俗名并不可靠（实测"脚气"→氢化可的松排在正确答案之后） |
| **向量召回没有下限** | kNN 永远返回 top-k，垃圾问题也会挑出三味药当证据喂给模型 | 重排分全体低于 -5 时返回空。**不能用向量相似度当闸**：实测"睡不着" 0.6228 vs "推荐个显卡" 0.6164，差 0.006，分不开 |

### 11.1 药品数据源盘点（2026-11 实测）

药品库要回答的是"这个药能不能吃、怎么吃、和别的药冲不冲突"，字段必须是说明书级的：适应症 / 用法用量 / 禁忌 / 不良反应 / 相互作用 / 疗程 / 停药指征 / OTC 属性。按这个标准把能找到的来源过了一遍：

| 来源 | 规模 | 关键字段 | 许可 | 结论 |
|---|---|---|---|---|
| **NMPA 数据下载页** | — | 只有「药品编码本位码」+ 器械备案 | 政府公开 | ❌ 没有说明书全量 |
| **NMPA 在线查询** | 全量 | 齐全 | 无开放授权 | ❌ 无 API、无批量 |
| **CMeKG 官网** | 19,853 味 | 齐全 | — | ❌ `cmekg.pcl.ac.cn`、`zstp.pcl.ac.cn:8002` 均 502 下线 |
| **CMeKG GitHub 镜像** | 17,496 味 | 见下表 | **无 license** | ⚠️ 能下，但脏 |
| **台湾 TFDA**（`tw-drug-labels-vision`） | 22,704 份仿單 | 17 字段齐全 | `license: other` | ⚠️ 繁体 + 台湾药名 + 授权不明 |
| **yuanyanyao / lvwzhen/medicine** | ~400 味 | 只有注册信息 | CC-BY-SA / MIT | ❌ 无临床字段 |
| **丁香园开放平台** | 全量 | 齐全 | 商业授权 | 💰 需签合同 |
| **天池 86819** | 中药说明书 | NER 标注 | CC-BY-**NC** | ❌ 非商用，且非结构化全文 |

CMeKG 镜像的字段覆盖（9,600 味西药）：适应症 8,564（89%）、不良反应 7,841（82%）、OTC 类型 5,534（58%）、禁忌 3,837（40%）、用法用量 3,519（37%）、药物相互作用 1,209（13%）。

**覆盖之外还有两个致命质量问题**：

1. **`OTC类型` 字段错到会出事故**。名称含抗生素关键词的 583 味里 328 味被标为 OTC（56%）；名称含注射类的 961 味里 621 味被标为 OTC（65%）。具体样本：`注射用盐酸环丙沙星 → 乙类OTC`、`阿奇霉素 → 甲类OTC`、`盐酸左氧氟沙星葡萄糖注射液 → 乙类OTC`。大量记录同时挂着 `["甲类OTC","乙类OTC"]`，逻辑上不可能，是聚合了多个规格的脏数据。**这个字段直接决定 agent 敢不敢推荐，导进去等于让 agent 建议用户自行购买注射用抗生素。**
2. **`用法用量` 大量截断**。`头孢克肟` 的用法用量只有一句「口服给药：」，剂量丢失。`适应症` 是实体列表且带碎片（「对头孢克肟敏感的链球菌属（肠球菌除外）」「敏感」「细菌」）。「适应症 + 用法用量含剂量 + 禁忌」三件套齐全的只有 1,636 味西药。

**结论：CMeKG 不导入。** 广度换来的是不可控的错误，而 `drug_info` 的价值恰恰在"准"。

**实际采用的方案：人工整理 + openFDA 双层。**

NMPA 说明书范本（官方、中文、字段对得上）在实测环境里拿不到——`nmpa.gov.cn` 被网络拦死，而存量范本都在 `wwwroot/` 下。解析器已经写好（`scripts/import_otc_labels.py`，纯 Python 解 Word97，不依赖 python-docx/antiword），能跑，等网络可达再补。

当前用 openFDA 补广度：它是**美国联邦政府作品，公有领域（CC0）**，可以随便用。

| 层 | 文件 | 数量 | 内容 |
|---|---|---|---|
| 人工整理 | `data/drugs.json` | 35（27 OTC + 8 处方） | 中文，按中国用药习惯写 |
| openFDA 导入 | `data/drugs-openfda.json` | 43（8 OTC + 35 处方） | 英文原文，美国市场标签 |

合并规则：同一通用名以人工整理的为准（剂量规格是按中国市场写的），openFDA 只补空位。加载器 `drugs.py` 校验两个文件，缺字段启动即失败。

**为什么大量导处方药**：这个 agent 的核心能力之一是判相互作用——"我在吃华法林，能不能再吃布洛芬"。只认识 OTC 答不了这类问题。openFDA 的处方药标签是 SPL 格式，`indications_and_usage` / `dosage_and_administration` / `contraindications` / `adverse_reactions` / `drug_interactions` 五个字段齐全，质量比 OTC 的 Drug Facts 格式好得多。

**导入时踩到的三个坑（都已处理）**：

1. **中文问句打不中英文正文**。BM25 跨不了语言——实测"痛风发作吃什么药"召回的是止痛药，不是别嘌醇/秋水仙碱（正文写的是 `gout`）；"他汀类"打不中 `atorvastatin`。向量模型也不稳。解法是给每味药手写**中文疾病/症状关键词**拼进 `aliases`，给中文问句一个字面锚点。**这是英文数据的必要补偿，不是可选项。**
2. **字段缺失不能表现成"没有"**。OTC 的 Drug Facts 格式没有禁忌栏，碳酸钙和褪黑素导出来 `contraindications` 是空的——如果入库，模型会以为"这药没有禁忌"。导入脚本直接跳过这类标签，宁可少两条。
3. **不能机器翻译**。翻译过的说明书不能当依据用——"contraindicated in patients with uncorrected hypoadrenalism" 翻错一个词就是医疗事故。正文保留英文原文，模型读英文、用中文回答，这个它做得到。

`drug_info` 输出也改了：空字段不输出那一行。原来"【疗程】"后面跟空白，模型会以为说明书写了疗程但被截断，转而自己编一个。

## 附录 A：为什么不用 Kafka

用户最初想引入 Kafka 贴近生产级。最终选择"账本表 + 投影"，理由：

- 单 broker 没有副本，Kafka 最核心的价值（持久化 + 重放 + 多消费者）全部落空。
- 事件溯源可以用 PostgreSQL 的账本表实现：`fact_ledger` 就是事件日志，`fact_current` 就是投影。语义等价，运维成本为零。
- 真实收益：少一个 1-2 GB 的 JVM 进程、少一套 partition/consumer group 调参、少一类"消息堆积"故障。
- 如果未来真的需要多消费者重放（比如离线分析、实时告警），再引入 Kafka，届时账本表可以直接作为事件源导出——**迁移路径是通的**。

| 维度 | 小荷 AI 医生 | 小团健康管家 | 本项目 |
|---|---|---|---|
| 核心交互 | 强制追问 | 家庭档案 + 履约闭环 | 强制追问 + 卡片化问诊 |

POST /api/v1/reports                    # multipart，异步

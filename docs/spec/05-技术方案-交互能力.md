# 技术方案 · 交互能力（v1.3）

日期：2026-11-26　｜　对应需求：`04-增量需求-交互能力.md`

---

## 1. 现状与约束

| 现状 | 影响 |
|---|---|
| 前端是单文件 `App.vue`（510 行） | 直接加 7 个功能会变成 900 行，不可维护 |
| `client.ts` 只解析 5 种 SSE 事件 | `agent`/`handoff`/`plan`/`continue` 被丢弃，徽标与交接提示是死的 |
| 后端无反馈表、无会话列表接口 | 反馈与会话管理都要新增 |
| `Decision.Clarify` 只有 `question` | 追问卡片需要扩展 |
| ArchUnit 卡分层：下层不得依赖 `platform.api` | 新包必须放在 `platform` 之下或独立 |

**硬约束**：不引入前端 UI 库、不改内核语义、不破坏现有 SSE 协议。

---

## 2. 总体思路

```
后端：薄增量                     前端：先拆再加
├─ 反馈：新包 + 1 张表          ├─ App.vue 只做壳
├─ 会话列表：仓储加一个查询      ├─ 视图/组件/composable 三层
└─ Clarify：加 options 字段      └─ 每个功能一个 composable 或 util
```

**为什么前端必须先拆**：7 个功能里有 5 个是"消息级操作"。
如果继续写在 `App.vue` 的模板里，每个功能都会往同一个 `v-for` 里塞分支，
最终没人敢改。先拆成 `MessageItem`，之后每个操作只改一个组件。

**为什么后端只做薄增量**：这些能力的复杂度都在交互侧，
后端只需要"存下来"和"给出来"，不该引入新的编排层。

## 3. 模块划分

### 3.1 后端新增

```
com.health.agent.platform.feedback/     ← 新包
├── FeedbackController.java             接收反馈、校验、落库
├── FeedbackRepository.java             写入与查询
└── Feedback.java                       领域记录
```

放在 `platform` 下而不是新建顶层包，理由：它依赖 `platform.api` 的错误类型与租户解析，
ArchUnit 规则要求"上层可以依赖下层"，反过来不行。

**会话列表**不新建包，扩展现有 `SessionStore` + `SessionRepository`：

```java
List<SessionSummary> listByOwner(String tenantId, String userId, int limit)
```

**分层规则**（写进 CR checklist）：

1. 组件不直接 `fetch`，只调 composable
2. composable 不碰 DOM，只调 api 与改状态
3. `utils` 纯函数，不依赖 Vue
4. `App.vue` 不出现业务逻辑

## 4. API 契约

### 4.1 提交反馈

```
POST /api/v1/feedback
X-Tenant-Id: {tenant}
{
  "sessionId": "s_xxx",
  "turn": 3,
  "agent": "doctor",
  "rating": "up" | "down" | "report",
  "reason": "不准确" | "不安全" | "太啰嗦" | "其他" | "内容问题",
  "comment": "可选，≤200 字"
}

200 {"ok": true}
400 参数非法（rating 不在枚举、sessionId 为空）
404 会话不存在或不属于当前租户
```

**幂等**：同一 `(session_id, turn, agent)` 覆盖，不新增行。唯一键保证。

### 4.2 会话列表

```
GET /api/v1/sessions?userId=u1&limit=20
X-Tenant-Id: {tenant}

200 {
  "sessions": [
    {"id":"s_xxx","turns":4,"preview":"我头疼三天了","updated_at":"2026-11-26T15:00:00"}
  ]
}
```

`preview` 取该会话第一条 USER 消息，截断 24 字。`turns` 用 `COUNT(DISTINCT turn)`。

### 4.3 追问候选（SSE 事件）

新增一种事件，在正文 token 之前发：

```
event: clarify
data: {"options":["持续不到一天","一到三天","超过一周"]}
```

**向后兼容**：老客户端不认识 `clarify`，忽略即可，正文照常收到。

### 4.4 停止生成

不新增接口。前端 `AbortController.abort()` 断开 SSE；
服务端写失败时 `SseEmitter` 抛 `IOException`，现有 `handle` 的 catch 会收尾。
需要补一条：写失败不再调用 `librarian.consolidateAsync`，避免把半截回答写进记忆。

## 5. 数据模型

```sql
CREATE TABLE IF NOT EXISTS message_feedback (
  id          BIGINT       NOT NULL AUTO_INCREMENT,
  tenant_id   VARCHAR(64)  NOT NULL,
  session_id  VARCHAR(32)  NOT NULL,
  turn        INT          NOT NULL,
  agent       VARCHAR(32)  NOT NULL DEFAULT '',
  rating      VARCHAR(16)  NOT NULL,          -- up / down / report
  reason      VARCHAR(32)  NOT NULL DEFAULT '',
  comment     VARCHAR(200) NOT NULL DEFAULT '',
  created_at  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at  DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_feedback (tenant_id, session_id, turn, agent),
  KEY idx_rating_time (rating, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='回答反馈';
```

**为什么冗余 `tenant_id`**：与 `message` 表一致。靠 `session_id` join 出租户，
漏写一次条件就是跨租户泄露，冗余一列换掉一类风险。

**为什么用 `turn + agent` 定位消息**：现在没有独立的 message id 暴露给前端。
用轮次 + 回答者足以唯一确定"哪条回答"，且不要求前端理解数据库主键。

## 6. 关键决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 分享图在哪生成 | 浏览器 canvas | 不上传用户问答内容到服务端，隐私风险最低 |
| 追问候选从哪来 | 模型在 `Clarify` 里一并给 | 不额外调一次模型；候选与追问同源，不会答非所问 |
| 反馈如何进评测 | 落表，后续由 ops 导出为 L1 语料 | 不在请求链路里跑评测，避免拖慢响应 |
| 消息删除 | 不做 | 需要消息级主键与级联，收益低于成本；举报已覆盖合规诉求 |
| 会话列表分页 | 先取 20 条，不分页 | 单用户场景，20 条足够；分页等有真实数据再加 |

## 7. 防腐化规则

这次增量最大的风险不是功能做不出来，是**把单文件改成更大的单文件**。
四条硬规则，写进 CR 检查：

1. **行数上限**：`App.vue` ≤ 120 行，组件 ≤ 220 行，composable ≤ 200 行。超了先拆再加。
2. **依赖方向**：组件 → composable → api/utils，禁止反向。
3. **状态单一来源**：消息只在 `useChat` 里，会话只在 `useSessions` 里，组件不存副本。
4. **新增功能先加 composable**：如果发现要在组件里写 `fetch` 或 `localStorage`，说明位置错了。

**迁移顺序**（每一步都要能编译、能跑）：

```
第 1 步：App.vue 拆出 ProfileDrawer（纯搬运，不改逻辑；ReportView 已在 v1.4 移除）
第 2 步：拆出 MessageItem + Composer + ChatView（仍不改逻辑）
第 3 步：加复制/反馈/分享/长按菜单（只动 MessageItem）
第 4 步：加追问卡片（动 ChatView + useChat）
第 5 步：加会话管理（新增 useSessions + Sidebar）
第 6 步：加停止/重试（动 useChat + Composer）
```

# 01 症状咨询域 · 技术规格

所属服务：core　｜　依赖：06 安全、02 医药知识、05 记忆档案、llm-gateway
对应需求：FR-02、FR-03、FR-04、FR-10

---

## 1. 范围与归属

### 1.1 职责

把"我不舒服"变成"要不要就医"。这个域是产品入口，也是路由质量的承载点——单意图准确率、多意图覆盖率、首段延迟，全部在这里落地。

### 1.2 输入输出

| 项 | 内容 |
|---|---|
| 输入 | 文本（≤2000 字），可带图片（转 03 域） |
| 输出 | 自由文本（流式），无固定结构 |
| 中间产物 | 路由结果、交接链、工具调用记录、`turn_event` |

**没有固定输出结构是当前设计，不是缺陷**。医疗建议的形态随场景变化（急症要短、慢病要细），强行套模板会让模型把内容往格子里塞。

### 1.3 明确不做

| 不做 | 归属 |
|---|---|
| 具体药品的用法用量 | 02 医药知识域 |
| 化验单指标判读 | 03 检查报告域 |
| 医院推荐、科室详情 | 04 就医路径域 |
| 图片识别 | 03 域（OCR） |
| 下诊断、给病名 | 产品边界，任何域都不做 |

### 1.4 与 `health-agent-design.md` 的关系

架构决策不重复。本节只补三处设计文档未展开、但直接影响实现的细节：

1. 路由与交接走同一条路径，区别只在发起者
2. 红旗命中后为什么不用模板话术
3. 多意图的队列在哪里维护

## 2. 领域模型

### 2.1 无独立表

本域不建表。状态全部落在 `session` 与 `turn_event`：

| 状态 | 存放位置 |
|---|---|
| 当前持有者 | `session.active_agent` |
| 对话历史 | `message` |
| 路由/交接/工具轨迹 | `turn_event` |
| 多意图队列 | **内存，不落库** |

**多意图队列为什么不落库**：它只在单轮内有效。落库会引入"跨轮待办"的语义，而用户下一轮可能换话题，待办就过期了。当前做法是 CLARIFY 时把剩余写进 `message`（`pending_kept` 事件），让下一轮的 agent 自己看到。

### 2.2 会话状态

```
S0 新建
  → S1 路由中（Manager 判断）
  → S2 执行中（execute agent 处理）
  → S3 已答复
  → S4 追问中（用户继续）
  → S1 / S2（从上一轮持有者续接，不过 Manager）
```

**关键差异**：S4 → S1 不是必经路径。多轮默认从 `active_agent` 续接，只有它主动交接时才回到路由。

### 2.3 三条不变量

1. **红旗判断先于路由**。任何"先分类再考虑急救"的实现都是错的。
2. **每段回答都要落库**。多意图会产生两段以上，只存最后一段，下一轮谁都看不到自己说过什么。
3. **`turn_event` 必须能还原决策链**。只记结果不记过程，出问题只能猜。

## 3. 核心算法与规则

### 3.1 路由判定

```
输入：用户原话 + 画像摘要
模型：managerModel（快模型）
输出：ROUTE{target, intent, remaining[]} | CLARIFY{question} | ANSWER{text}
```

**目标集合**：`doctor` / `pharma` / `report` / `care`。

**判定规则**（写进 prompt，不是代码）：

| 情况 | 选择 |
|---|---|
| 先有症状，想知道吃什么药 | `doctor`（要先判断病情） |
| 已知药名，只问这个药 | `pharma` |
| 报告、指标、化验单 | `report` |
| 明确问"去哪""挂什么科" | `care` |
| 拿不准 | `doctor`（问诊能覆盖问药，反过来不行） |

**为什么不用规则做业务意图**：规则做"要不要送进模型"，模型做"送给谁"。混在一起，规则表会膨胀到无法维护。

### 3.2 红旗识别

```
RedFlagScanner.scan(text, age) → Optional<RedFlag>
  ├─ 命中 → 注入 hint 到上下文（不直接回复）
  └─ 未命中 → 空
```

**命中后不套模板**，而是把信号作为提示注入，由模型组织语言。

理由：模板会"过度肯定"。系统只看到一句话，不知道这是不是正在发生、是不是在转述别人的事、是不是电影情节。用模板替用户下结论，是拿"看起来很专业"换"实际上不负责"。

红旗清单在 `prompts/fragments/redflag.md`，doctor / pharma / care 三处引用。

### 3.3 工具选择

| 工具 | 何时用 | 何时不用 |
|---|---|---|
| `knowledge_search` | 疾病、检查、治疗、注意事项 | 具体药品（交 pharma） |
| `health_record` | 判断用药安全前、需要既往史 | 用户明确说没有相关病史 |
| `daily_context` | 护理建议需要季节/天气 | 与时间无关的问题 |

**职责不重叠是交接的前提**。给 doctor 挂 `drug_info` 会让它在本地库没命中时卡住，而不是交接出去。

### 3.4 多意图处理

```
Manager 拆出 remaining（最多 2 条）
  → 主诉求执行完
  → 队列非空 → 交接下一个，发 continue 事件
  → 中途 CLARIFY → 剩余写进历史（pending_kept），本轮结束
```

**为什么只让 Manager 拆**：执行中的 agent 只看得到局部上下文，拆出来的诉求容易和主诉求重复。它想补充诉求，走交接就够了。

**为什么串行不并行**：用药建议依赖病情判断。并行会让两边在不知道对方结论的情况下各说各话。

### 3.5 输出约束

| 约束 | 实现 | 兜底 |
|---|---|---|
| 不出现断言式病名 | prompt 约束 | SafetyGate 规则扫描 |
| 不推荐处方药 | 职责边界（交 pharma） | SafetyGate |
| 急症首句给指令 | prompt 片段 | 无（依赖模型） |
| 信息不足时追问 | prompt 约束 | 无 |

**最后两行没有兜底**，是当前已知缺口：模型没照做时，系统无法纠正。见第 7 节。

## 4. 接口与事件

### 4.1 对外

| 接口 | 说明 |
|---|---|
| `POST /api/v1/sessions` | 创建会话，返回 `session_id` |
| `POST /api/v1/sessions/{id}/messages` | 发消息，SSE 流式 |
| `GET /api/v1/sessions/{id}` | 历史（只返回 USER/ASSISTANT） |
| `GET /api/v1/sessions/{id}/timeline` | 按轮合并消息与事件 |

### 4.2 SSE 事件

| 事件 | 载荷 | 用途 |
|---|---|---|
| `agent` | `{agent, turn, resumed}` | 本轮从谁开始 |
| `handoff` | `{from, to}` | 交接发生 |
| `plan` | `{remaining[]}` | Manager 拆出了多意图 |
| `continue` | `{next, intent}` | 上一段答完，下面还有一段 |
| `tool` | `{name, ok}` | 工具调用 |
| `token` | `{delta}` | 流式正文 |
| `turn_end` | `{status, agent}` | 本轮结束 |
| `done` | `{turn, safety_issues, streamed}` | 整体完成 |

**`continue` 与 `handoff` 必须分开**：`handoff` 在普通路由时也会发，前端分不清"换人"和"同一轮的第二段"。

### 4.3 turn_event 类型

`turn_start` / `agent_start` / `agent_end` / `route` / `handoff` / `handoff_rejected` / `plan` / `pending_kept` / `tool_start` / `tool_end` / `answer` / `clarify` / `turn_end`

**每个事件的 `detail` 必须有足够信息还原决策**。例如 `route` 要带 `to`、`reason`；`handoff` 要带 `from`、`to`、`reason`。

## 5. 异常与降级

| 场景 | 行为 | 用户看到 |
|---|---|---|
| 模型超时 | `degraded("timeout")` | "处理超时了，可以再试一次" |
| 步数耗尽（无剩余） | `degraded("max_steps_reached")` | "需要多步处理，拆成更具体的问题" |
| 步数耗尽（有剩余） | `degraded("partial_done")` | "处理了一部分，剩下的请单独发" |
| 交接目标不存在 | 拒绝交接，错误喂回模型 | 无感知 |
| 模型不可用 | 离线模式 | 固定话术 |
| 流式中断 | 已发内容保留，`turn_end` 记 `running` | 无感知（客户端超时） |

**`running` 状态是个埋点缺口**：被过滤的请求不写 `turn_end`，timeline 永远停在 running。不影响用户，但会让统计失真。

## 6. 验收口径

### 6.1 指标表

| ID | 判定标准 | 测试集 | 判定方式 | 谁判 |
|---|---|---|---|---|
| SC-01 | 主路由准确率 100% | 197 条构造单意图（4 能力各约 50） | 首个非 manager 的 agent 等于期望值 | 自动 |
| SC-02 | 真实分布主路由 ≥60% | 402 条真实提问 | 同上，人工复核错例是否为标注噪音 | 自动 + 抽检 |
| SC-03 | 两意图完整覆盖 ≥60% | 120 条构造双意图 | 期望能力集合 ⊆ 实际出现集合，不要求顺序 | 自动 |
| SC-04 | 三意图不劣化 | 24 条构造三意图 | 至少覆盖 2 个；降级时必须出现 `partial_done` 或说明 | 自动 |
| SC-05 | 红旗首句给指令 | 50 条红旗构造用例 | 第一句含"就医/急救/120"等行动词 | 人工 |
| SC-06 | 多段回答全落库 | 30 条多意图 | assistant 消息数 = 回答段数 | 自动 |
| SC-07 | 首段延迟 | 线上真实流量 7 天 | 到第一个有信息量的 token，P95 ≤6s | 自动 |
| SC-08 | 降级率 | 全量 | `degraded` 占比 ≤5% | 自动 |

### 6.2 当前实测（v1.1，1000 条）

| 指标 | 实测 | 达标 |
|---|---|---|
| SC-01 主路由（构造） | 100% | ✅ |
| SC-02 主路由（真实） | 60.9%（含标注噪音） | ⚠️ 边界 |
| SC-03 两意图覆盖 | 23.3%（28/120） | ❌ |
| SC-04 三意图 | 0%（0/24） | ❌ |
| SC-07 首段延迟 | P90 12.7s / P99 20.1s | ❌ |
| SC-08 降级率 | 4.9%（49/1000） | ✅ |

**SC-03 的 23.3% 是修复前的数字**。v1.1 加了 remaining 队列后未做全量回归，需重跑确认。

### 6.3 判定细则

**"部分正确"怎么算**：SC-03 要求集合包含，不要求顺序。例如期望 `[doctor, care]`，实际 `[care, doctor]` 算通过；实际只有 `[doctor]` 算失败。

**为什么不用序列**：要求顺序会把合法的其他路径判成失败——这是"线性顺序误判并行"的同类错误。

## 7. 依赖与风险

| 依赖 | 风险 | 缓解 |
|---|---|---|
| managerModel | 路由判错 | 接手方有交接权，可转走；代价是多一次调用 |
| 红旗规则 | 漏报 | 规则 + prompt 双保险；规则漏了 prompt 还能兜 |
| 知识库 | 检索不到导致答非所问 | 检索失败时明确说"查不到"，不编 |
| 模型遵循度 | 急症首句、追问策略没照做 | **无兜底**，只能靠评测发现 |

**最大的技术风险：输出约束没有兜底。** 急症首句给指令、信息不足时追问，这两条全靠模型遵循 prompt。模型没照做，系统无法纠正。

缓解方向（不在本版）：把"是否追问"做成结构化判定（类似路由），而不是让模型自由发挥。

**最大的质量风险：真实数据标注噪音。** SC-02 的 60.9% 里，人工核验后约一半是标注错误（关键词标成"用药咨询"，实际是症状描述）。这不该改 Agent，该修标注——属于评测体系迭代，不是能力问题。

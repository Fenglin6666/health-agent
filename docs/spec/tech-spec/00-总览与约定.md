## 1. 这套文档解决什么

`03-技术方案.md` 回答"系统怎么落地"：服务怎么拆、表怎么建、怎么部署。
这套域规格回答"**每个域具体怎么实现、怎么测、边界在哪**"。

两者不重复：系统级决策只在 03 写一次，这里只写落地。

每个域一份，统一七节：

```
1. 范围与归属   2. 领域模型   3. 核心算法与规则
4. 接口与事件   5. 异常与降级  6. 验收口径   7. 依赖与风险
```

**第 6 节是重点**。需求规格给的是"≥60%""≤6s"这类数字，但没给测什么集、怎么判、谁判。域规格必须把这些补齐，否则开发和测试对不齐，最后变成"我觉得达标了"。

## 4. 全局约定

### 4.1 标识

| 类型 | 前缀 | 示例 | 现状 |
|---|---|---|---|
| 会话 | `s_` | `s_fc00672f2c6a4b2d` | ✅ 已是 |
| 消息 | 自增 BIGINT | — | ✅ |
| 结论 | 无 | — | ❌ 当前没有独立的结论实体 |
| 事实 | 自增 BIGINT | — | ✅ |

**结论实体缺失是个问题**：当前结论只存在于 assistant 消息里，无法单独引用、无法做版本比对。域规格 01 会说明影响。

### 4.2 时间

- 存储：`DATETIME(3)`，服务器时区
- 传输：ISO 8601 带时区
- 业务日期（报告日期、用药起始）：`DATE`，不带时区

### 4.3 错误响应

当前用 Spring 默认结构，没有统一错误码。**目标**：

```json
{"code": "11001", "message": "...", "retryable": true, "trace_id": "..."}
```

| 段 | 域 |
|---|---|
| `10xxx` | 通用 / 网关 |
| `11xxx` | 症状咨询 |
| `12xxx` | 医药知识 |
| `13xxx` | 检查报告 |
| `14xxx` | 就医路径 |
| `15xxx` | 记忆档案 |
| `16xxx` | 安全合规 |
| `17xxx` | 运营质量 |

### 4.4 日志与事件

每条结构化日志必带：`trace_id`、`session_id`、`tenant_id`、`agent`、`latency_ms`。

`turn_event` 是排障主依据，事件类型见 01 域 4.3。

### 4.5 租户上下文

- 来源：凭证解析，**不信任请求头**（详见 10 域）
- 传递：进入编排层前固定，下游只读
- 兜底：DAO 层统一注入租户条件

## 5. 统一的验收口径写法

```
指标 ID | 判定标准 | 测试集 | 判定方式 | 谁判
SC-01  | ≥60%    | 120 条双意图构造用例 | 集合包含判定（不要求顺序） | 自动
```

四个字段缺一不可：

| 字段 | 必须回答 |
|---|---|
| 测试集 | 多少条、怎么构成、有没有标注噪音 |
| 判定方式 | 自动 / 人工 / 规则；部分正确算不算 |
| 谁判 | 算法 / 产品 / 医学 |
| 失败怎么算 | 部分完成是 pass 还是 fail |

**没有这四个字段的验收项，不允许进门禁**——它一定会在验收时变成争论。

## 7. 与 `03-技术方案.md` 的一处冲突

`03` 里写了"3+2 服务"，本套域规格按**代码包**划分域，两者粒度不同：

- 域是**逻辑边界**（一个域可能落在 core 里，也可能跨 core 和 knowledge）
- 服务是**部署边界**（3+2）

一个域跨两个服务是允许的（如 02 医药知识域：编排在 core，检索在 knowledge），但**不能反向依赖**。

# 05 记忆与档案域 · 技术规格

所属服务：core　｜　依赖：无（被其他域依赖）
对应需求：FR-08

---

## 1. 范围与归属

### 1.1 职责

记住用户说过的健康事实，跨会话可用；新事实与旧事实冲突时提示确认。

**这个域决定产品是不是"个人"健康管家**。没有它，每次对话都是陌生人。

### 1.2 输入输出

| 项 | 内容 |
|---|---|
| 输入 | 对话内容、用户确认/否认 |
| 输出 | 画像摘要（注入 prompt）、矛盾提示、档案查询结果 |
| 中间产物 | 事实账本、投影、矛盾记录 |

### 1.3 明确不做

| 不做 | 理由 |
|---|---|
| 自动推断未明说的信息 | 医疗场景推断错误代价高 |
| 覆盖式更新 | 历史本身就是信息 |
| 跨用户共享 | 租户隔离的底线 |

### 1.4 四层记忆

| 层 | 内容 | 存放 |
|---|---|---|
| transcripts | 原文 | `message` |
| notes | 抽取的要点 | `fact_ledger` |
| representations | 画像投影 | `fact_current` + `ProfileAggregator` |
| injected | 注入 prompt 的摘要 | `DigestBuilder`（运行时生成） |

## 2. 领域模型

### 2.1 事实账本（append-only）

| 字段 | 说明 |
|---|---|
| `owner` | `tenant:user` |
| `fact_type` | allergy / medication / condition / habit |
| `fact_key` | 事实名（如"青霉素过敏"） |
| `fact_value` | 事实值 |
| `confidence` | 抽取置信度 |
| `evidence` | 原文片段 |
| `session_id` | 来源 |

**只插入，不更新，不删除**（软删除外）。

### 2.2 投影

`fact_current(owner, fact_key)` → 指向最新的 `ledger_id`。

**投影可随时重建**：删掉它，从账本重放即可。这是 append-only 的核心价值——投影错了能重算，账本错了就永久错。

### 2.3 矛盾

| 字段 | 说明 |
|---|---|
| `kind` | value_conflict（值冲突）/ temporal_conflict（时间冲突） |
| `severity` | high / medium / low |
| `old_value` / `new_value` | 冲突双方 |
| `status` | open / confirmed / dismissed |

### 2.4 三条不变量

1. **事实只追加**。修订 = 新增一条 + 指向被修订的 ID。
2. **矛盾必须能追溯到两条 Fact**。只记"有矛盾"无法判断谁对。
3. **画像摘要不落库**。每次运行时从投影生成，避免摘要与投影漂移。

## 3. 核心算法与规则

### 3.1 抽取

```
对话结束 → Librarian 抽取
  ├─ 只抽明确陈述（"我对青霉素过敏"）
  ├─ 不抽推测（"我好像有点过敏"→ 低置信，不写账本）
  └─ 记录 evidence（原句），便于回溯
```

**低置信不写账本**，写入只会污染档案。宁可漏记，不可错记。

### 3.2 矛盾检测

```
新事实 vs 投影
  ├─ 值不同且同 key     → value_conflict
  ├─ 时间上互斥         → temporal_conflict
  └─ 一致               → 更新投影
```

**检出后不自动覆盖**。写进画像首部"待确认"，用户确认后才更新投影。

### 3.3 注入

```
DigestBuilder.build(owner)
  ├─ 只注入高置信事实
  ├─ 按类型分组（过敏 / 长期用药 / 慢病）
  └─ 矛盾项置顶，标注"待确认"
```

**注入要短**。画像摘要进 prompt，太长会挤占对话历史，且模型对长摘要的遵循度下降。

### 3.4 双实现问题

当前 `InMemoryFactLedger` 与 `JdbcFactLedger` 并存，默认取决于配置。

**这是一个必须消除的隐患**：默认走内存时，重启丢档案，而用户不会知道。详细设计里必须写死默认 JDBC，内存实现只用于单测。

## 4. 接口与事件

### 4.1 内部调用

| 接口 | 用途 |
|---|---|
| `health_record` | 其他域查档案（只读） |
| `GET /api/v1/memory/{userId}` | 后台查看（需审计） |
| `POST /api/v1/memory/{userId}/confirm` | 用户确认矛盾 |

### 4.2 事件

| 事件 | 载荷 |
|---|---|
| `fact_recorded` | `{owner, fact_key, confidence}` |
| `contradiction_found` | `{owner, kind, severity}` |
| `contradiction_resolved` | `{owner, status}` |

**`fact_recorded` 必须记 `evidence` 的哈希**，用于验证"这条事实确实来自那句原文"。

## 5. 异常与降级

| 场景 | 行为 |
|---|---|
| 抽取失败 | 不写账本，记日志，不影响本轮回答 |
| 投影与账本不一致 | 重建投影（可自动） |
| 矛盾过多（>5 条未处理） | 只提示最高 severity 的一条，不刷屏 |
| 档案为空 | 明确说"还没有你的健康记录"，不假装知道 |

## 6. 验收口径

| ID | 判定标准 | 测试集 | 判定方式 | 谁判 |
|---|---|---|---|---|
| PF-01 | 事实只追加 | 20 次修改同一事实 | `fact_ledger` 行数 = 修改次数 + 1 | 自动 |
| PF-02 | 投影可重建 | 删除投影后重放 | 重建结果与删除前一致 | 自动 |
| PF-03 | 矛盾检出率 | 30 条构造冲突 | 检出 ≥90%，误报 ≤5% | 自动 |
| PF-04 | 矛盾不自动覆盖 | 10 条冲突 | 投影在用户确认前不变 | 自动 |
| PF-05 | 跨会话恢复 | 10 组隔日会话 | 画像摘要包含上一轮事实 | 自动 |
| PF-06 | 低置信不写账本 | 20 条模糊表述 | `fact_ledger` 无新增 | 自动 |
| PF-07 | 默认实现正确 | 重启服务 | 事实仍在（证明走 JDBC） | 自动 |

**PF-07 是针对双实现隐患的验收项**。没有这一条，默认走内存的问题会一直潜伏到某次重启。

## 7. 依赖与风险

| 依赖 | 风险 | 缓解 |
|---|---|---|
| 抽取模型 | 漏抽、错抽 | 只抽明确陈述；低置信不写 |
| 账本增长 | 长期膨胀 | 不分区、不清理（它是用户健康史） |
| 画像注入 | 太长挤占上下文 | 限长 + 只注入高置信 |

**最大的风险：记忆错了比没记忆更糟。** 用户说"我对青霉素过敏"，系统记成"对青霉素不过敏"，后果是实打实的。

缓解：矛盾检测 + evidence 回溯 + 用户确认。但**没有"记忆正确性"的自动校验**——这只能靠抽检。

# 07 运营与质量域 · 技术规格

所属服务：ops　｜　依赖：core（只读）、11 评测与观测
对应需求：FR-12

---

## 1. 范围与归属

### 1.1 职责

回答"这次改动有没有变差"。三件事：跑批、基线对比、badcase 归集。

### 1.2 输入输出

| 项 | 内容 |
|---|---|
| 输入 | 评测集、待测版本快照、基线版本 |
| 输出 | 通过率、逐例 diff、失败清单 |
| 中间产物 | `eval_run` / `eval_result` |

### 1.3 不参与在线链路

本域只在后台运行，不进用户请求的同步路径。

### 1.4 当前实现的程度

`EvaluationRunner` 三档：

| 档 | 测什么 | 现状 |
|---|---|---|
| 红旗 | 规则命中 | ✅ 正向要求 100% |
| 事实校验 | 回答里的药名能否在知识库找到 | ✅ 抓"编了一个不存在的药" |
| 客观题 | 有标准答案的知识题 | ✅ 测模型底子 |

**刻意不做 LLM 互评**：用模型判模型，测的是两个模型的一致性，不是正确性。

**缺口：不测路由。** 路由评测目前靠外部脚本（`.data/medeval/`），不在主工程内，改完路由无法一键回归。

## 2. 领域模型

### 2.1 表

| 表 | 作用 |
|---|---|
| `eval_set` | 评测集（名称、层、负责人） |
| `eval_case` | 单条用例（输入、前置条件、期望、判分方式） |
| `eval_run` | 一次跑批（快照、基线、时间） |
| `eval_result` | 单条结果（通过、证据、diff） |
| `badcase` | 线上问题（来源、归因分类、状态） |

### 2.2 三条不变量

1. **跑批必须走真实链路**。mock 掉只能测代码逻辑，测不出"规则包 + 模型 + 知识版本"组合后的表现。
2. **必须有基线**。只看"这次 96%"没有意义，要看"比上次多了哪 3 例失败"。
3. **判分器变更要留校准记录**。没有校准的判分器，门禁是假的。

## 3. 核心算法与规则

### 3.1 跑批

```
run(setId, snapshot) → EvalRun
1. 固定快照：config_version + model + prompt_hash + kb_version
2. 并发 8 逐例执行（真实链路）
3. 判分：
   rule  → 自动比对
   human → 进人工队列
   both  → 先自动，不一致转人工
4. 输出：passed/failed + 逐例 diff + 与基线的差异
```

### 3.2 门禁

| # | 指标 | 阈值 | 数据来源 |
|---|---|---|---|
| 1 | 红旗召回 | 100% | 专项集 |
| 2 | 主路由准确率 | 100%（构造集） | 跑批 |
| 3 | 多意图覆盖 | ≥60% | 跑批 |
| 4 | 结构完整（多段落库） | 100% | 跑批 |
| 5 | 降级率 | ≤5% | 线上统计 |
| 6 | 首段延迟 | P95 ≤6s | 压测或线上 |

**第 1 项和第 2 项要求 100%**：都是确定性判定（规则命中、集合包含），没有"95% 合理"的说法。

### 3.3 badcase 归集

| 来源 | 触发 | 自动化 |
|---|---|---|
| 自动扫描 | 降级、路由异常、Safety 命中 | 全自动入池 |
| 人工抽检 | 每日 1% | 半自动 |
| 用户举报 | 预留接口 | 全自动 + 24h SLA |

**归因分类必须强制选择**：`knowledge / wording / rule / model / data / product`。不选分类的不允许关闭——否则池子会变成"处理完了但不知道为什么"。

## 4. 接口与事件

| 接口 | 用途 |
|---|---|
| `POST /v1/eval/runs` | 创建跑批 |
| `GET /v1/eval/runs/{id}` | 结果与 diff |
| `GET /v1/badcase` | 池子查询 |

| 事件 | 触发 |
|---|---|
| `eval.run.finished` | 跑批结束 |
| `badcase.created` | 新 badcase 入池 |

---

## 5. 异常与降级

| 场景 | 行为 |
|---|---|
| 单例执行失败 | 记 `status=error`，不计入分母，单独统计错误率 |
| 错误率 >10% | 整批标记 `invalid`，不参与门禁 |
| 判分器抛异常 | 判 `unable_to_judge`，不判失败 |
| 基线缺失 | 允许跑，但结果不参与门禁 |

## 6. 验收口径

| ID | 判定标准 | 测试集 | 判定方式 | 谁判 |
|---|---|---|---|---|
| OP-01 | 跑批可对比 | 2 个版本 | 输出逐例 diff + 汇总 | 自动 |
| OP-02 | 门禁可阻断 | 构造 6 个不达标版本 | 每个都被阻断，提示具体项 | 自动 |
| OP-03 | 路由评测在主工程内 | 197 条构造集 | 一条命令跑完 | 自动 |
| OP-04 | badcase 强制分类 | 30 条入池 | 未分类的不允许关闭 | 自动 |
| OP-05 | 判分器可校准 | 1 个判分器 | 有校准集与一致率记录 | 人工 |

**OP-03 是本版新增的验收项**。当前路由评测在外部脚本里，改完路由要手动跑，容易漏。

## 7. 依赖与风险

| 依赖 | 风险 | 缓解 |
|---|---|---|
| 评测集 | 标注质量差导致门禁失效 | 每条必须写 `reason`；每月复核 10% |
| 模型版本 | 供应商静默升级导致漂移 | 每次 run 记 `model_version` |
| 人工 | 抽检与标注人力密集 | 先做 rule 可判的部分（约 70%） |

**最大的运营风险：评测集腐化。**

上线三个月后，模型和规则都变了，用例还是老的，门禁就变成"过时的考试"。

缓解：每月从 badcase 抽 20 条补充，同时淘汰 20 条已稳定通过的——保持**区分度**，不是数量。

判据：一条用例连续 10 次通过，它就不再提供信息，该退役或加难度。

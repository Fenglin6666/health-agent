## 0. 文档说明

### 0.1 这份文档定义什么

产品要做什么、做到什么程度算达标。

每条需求必须能回答三个问题：**给谁用、解决什么、怎么判定做到了**。答不上这三个的，不进这份文档。

### 0.2 这份文档不定义什么

| 不定义 | 归属 |
|---|---|
| 技术选型、组件划分、部署形态 | 技术方案 |
| 类结构、调用时序、接口签名 | 详细实现设计 |
| 当前实现到哪一步 | 内循环 CR 报告、外循环验收单 |

### 0.3 优先级

| 级别 | 含义 | 不达标的后果 |
|---|---|---|
| **P0** | 必须做到 | 阻断发布 |
| **P1** | 应该做到 | 记录，下个版本补 |
| **P2** | 可以做到 | 不影响发布 |

## 1. 产品定义

### 1.1 一句话

一个能记住你、能查资料、会拒绝的健康咨询助手——**不做诊断，做信息整理与风险提示**。

### 1.2 目标用户

| 用户 | 他要解决的事 | 频次 |
|---|---|---|
| 有具体不适、想知道要不要就医的人 | 症状 → 风险分级 → 就医建议 | 高 |
| 拿到报告看不懂的人 | 指标 → 解读 → 下一步 | 中 |
| 在吃药或准备吃药的人 | 药名 → 用法/禁忌/相互作用 | 中 |
| 要去看病但不知道挂什么科的人 | 症状 → 科室 → 就近医院 | 低 |

**机构用户**（租户）：一套部署服务多个机构，各机构的数据互不可见。当前只有个人用户，但隔离机制必须从一开始就在——事后补隔离，等于把所有查询重写一遍。

### 1.3 能力边界

**做**：

- 症状的风险分级（不是诊断）
- 药品说明书的客观信息转述
- 检查指标的参考区间对照
- 就医路径建议（科室、时机）

**不做**（每条都有决策依据，不是遗漏）：

| 不做 | 理由 |
|---|---|
| 下诊断、给病名 | 诊断需要资质，且一句话无法排除 |
| 推荐处方药品种 | 处方药只能讲说明书，不能推荐 |
| 给儿童/孕妇具体剂量 | 剂量依赖体重与肝肾功能，线上无法安全判断 |
| 替代医生做治疗决策 | 产品的价值是"帮你判断要不要去"，不是"帮你治" |
| 语音输入 | 当前范围只支持文本 + 图片 |

### 1.4 合规边界

- 不做医疗广告，不导流到特定医院
- 医院推荐只给位置、科室、等级，不给号源与排队时长
- 所有输出必须能被理解为"建议"而非"结论"

## 2. 用户旅程

### 2.1 主旅程：一次症状咨询

```
用户描述症状
  → 系统判断风险等级
  → 系统判断该由谁处理
  → 给出建议（含"要不要就医"）
  → 用户追问，系统记得上一轮说过什么
```

**需求约束**：

- 风险判断必须先于意图判断。不能先分类再考虑要不要急救。
- 用户追问时，系统必须知道"刚才说到哪了"，不能从头问一遍。

### 2.2 次旅程：报告解读

```
用户口述指标或上传图片
  → 系统识别指标与单位
  → 对照参考区间分级
  → 给出解读与复查建议
```

**需求约束**：单位无法识别时，明确说"看不懂这个单位"，不猜。

### 2.3 次旅程：用药咨询

```
用户给药名
  → 系统确认这是不是处方药
  → 非处方：给用法、禁忌、可选品种
  → 处方药：只转述说明书，不推荐品种
```

**需求约束**：处方属性以药品库为准，不靠模型记忆。

### 2.4 次旅程：就医路径

```
用户问"挂什么科 / 附近哪家医院"
  → 给科室建议
  → 需要具体地点时，问位置或使用已有位置
  → 给医院列表（含"去前电话确认"提示）
```

**需求约束**：只问科室时不追问位置——用户没要附近医院，多问一句就是让他白等一轮。

## 3. 功能需求

### FR-01 会话管理（P0）

| 项 | 内容 |
|---|---|
| 描述 | 创建会话、发送消息、读取历史、读取完整时间线 |
| 验收 | ① 会话可跨进程重启恢复；② 同一会话的消息顺序稳定；③ 会话轮次不设上限 |

**为什么轮次不设上限**：医疗问诊天然是多轮，截断等于逼用户重开，重开就丢上下文。

### FR-02 意图路由（P0）

| 项 | 内容 |
|---|---|
| 描述 | 判断用户这句话该由哪种能力处理 |
| 能力 | 症状与疾病 / 具体药品 / 指标与报告 / 科室与地点 |
| 验收 | ① 构造集（单意图、表达清晰）主路由准确率 100%；② 每次路由有可追溯的判断依据；③ 判错时接手方能把问题转走，不卡住 |

**需求约束**：路由结果必须可观测、可回归。不能是"模型自己知道"。

### FR-03 多意图处理（P1）

| 项 | 内容 |
|---|---|
| 描述 | 一句话含多个独立诉求时，全部处理，而不是只答一个 |
| 验收 | ① 两意图场景完整覆盖率 ≥60%；② 三意图场景允许降级为"答主诉求 + 明确说明剩余"；③ 降级时用户能看到"还有一部分没处理" |

**需求约束**：

- 拆错比不拆更糟——多一次交接就多一次等待。
- 同一件事的不同侧面不算多意图（"头疼吃什么药"是一件事）。

### FR-04 症状咨询（P0）

| 项 | 内容 |
|---|---|
| 描述 | 根据症状给出风险分级、护理建议、是否就医 |
| 验收 | ① 红旗场景第一句给出急救指令；② 不出现断言式病名（"你这是 XX 病"）；③ 信息不足时追问，不硬答 |

### FR-05 用药咨询（P0）

| 项 | 内容 |
|---|---|
| 描述 | 已知药名时，给出用法、副作用、相互作用 |
| 验收 | ① 处方药不推荐品种；② OTC 推荐必须来自药品库标注为非处方的条目；③ 儿童/孕妇不给具体剂量 |

### FR-06 报告解读（P0）

| 项 | 内容 |
|---|---|
| 描述 | 指标归一化、对照参考区间、给出分级与复查建议 |
| 验收 | ① 单位换算只走白名单；② 未识别单位不判读；③ 分级标准可解释（临界/异常有明确阈值） |

### FR-07 就医路径（P1）

| 项 | 内容 |
|---|---|
| 描述 | 科室建议、就近医院与药店 |
| 验收 | ① 只问科室时不追问位置；② 医院信息只含位置/科室/等级；③ 输出带"去前电话确认"提示 |

### FR-08 记忆与档案（P0）

| 项 | 内容 |
|---|---|
| 描述 | 记住用户说过的健康事实，跨会话可用；新事实与旧事实冲突时提示确认 |
| 验收 | ① 关键事实只追加不覆盖；② 矛盾能检出并提示；③ 用户确认后矛盾消失；④ 跨会话能恢复 |

### FR-09 安全闸门（P0）

| 层 | 要求 | 验收 |
|---|---|---|
| 红旗识别 | 路由之前 | 红旗召回率 100%（构造集） |
| 域外过滤 | 路由之前 | 明确非医疗的请求不进模型 |
| 输出审查 | 生成之后 | 不出现处方推荐、断言诊断、剂量 |

**需求约束**：安全判断不用 LLM，用规则。理由是可解释、可回归、毫秒级。

### FR-10 降级与兜底（P0）

| 场景 | 要求 |
|---|---|
| 超时 | 明确告诉用户超时，不返回半截内容 |
| 步数耗尽 | 说明"需要多步处理"，不是"没找到答案" |
| 部分完成 | 说明"处理了一部分，剩下请单独发" |
| 模型不可用 | 进入离线模式，给固定话术 |

### FR-11 检索（P0）

| 项 | 内容 |
|---|---|
| 描述 | 知识检索支持关键词与语义两路，融合后重排 |
| 验收 | ① 中间件不可用时降级到内存实现，不阻断启动；② 召回结果带来源；③ 重排只提升正分候选，不制造假阳性 |

### FR-12 评测（P1）

| 项 | 内容 |
|---|---|
| 描述 | 评测入口统一在主工程内，可一键回归 |
| 验收 | ① 红旗、路由、结构完整性三类可自动判；② 跑批结果可与基线 diff；③ 判分器变更需回放历史样本 |

### FR-13 多租户隔离（P0）

| 项 | 内容 |
|---|---|
| 描述 | 一套部署服务多个租户，租户之间数据、配置互不可见 |
| 验收 | ① 跨租户读写返回 403，不泄露"存在但无权"与"不存在"的区别；② 租户身份从凭证解析，不信任请求头；③ 每租户可指定独立的配置版本（规则包、prompt）；④ 删除租户时级联清理其全部数据 |

**三条硬约束**：

1. **租户身份不可由客户端声明**。当前 `X-Tenant-Id` 直接来自请求头且无校验——任何人构造一个值就能读写他人数据。这是越权漏洞，与"做不做多租户"无关，必须修。
2. **隔离在数据层兜底，不只在应用层**。所有查询强制带租户条件，漏一处就是事故。应用层校验是第二道，不是唯一一道。
3. **配置隔离用版本指针，不用副本**。每租户记录一个 `config_version`，指向同一份配置的不同版本；不为每个租户复制一套 prompt。

**明确不做**：计量计费（L4）。没有真实付费租户时做计量是空转，等有第一个机构客户再做。

## 4. 非功能需求

| ID | 指标 | 目标 | 优先级 |
|---|---|---|---|
| NFR-01 | 模型首 token（TTFT） | P90 ≤2s | P1 |
| NFR-02 | 端到端首段 | P95 ≤6s | P0 |
| NFR-03 | 可用性 | 中间件缺失时：知识服务降级、主服务明确失败 | P0 |
| NFR-04 | 可观测 | 每轮可还原：经过哪些能力、调了哪些工具、每步耗时 | P0 |
| NFR-05 | 成本 | 单轮模型调用 ≤2 次（多意图 ≤3 次） | P1 |
| NFR-06 | 数据安全 | 个人健康信息加密存储；日志不落原文 | P0 |

**NFR-02 的口径**：以"用户看到第一段有信息量的文字"为准，不是首字节。首字节可以是一条 meta 事件，用户感知不到。

## 5. 数据与合规

| 项 | 要求 |
|---|---|
| 个人健康信息 | 加密存储，字段级 |
| 会话内容 | 保留原文（记忆与矛盾检测需要），但不可导出原文 |
| 日志 | 只落 ID 与摘要，不落用户原文 |
| 删除权 | 用户删除会话时，级联删除事实账本与画像 |
| 审计 | 内部查看会话需工单 + 限时 + 全程审计 |

## 7. 本版验收判据

**不是"功能变多"，是"流程走完"**。五类产物齐全：

| # | 产物 | 判据 |
|---|---|---|
| 1 | 需求规格 | 本文档 |
| 2 | 技术方案 | 服务划分、数据模型、关键决策齐全 |
| 3 | 详细实现设计 | 三条关键链路的时序 + 接口签名 |
| 4 | 内循环产物 | CR 报告 + 门禁报告，各有结论 |
| 5 | 外循环产物 | 执行报告 + 缺陷单 + 验收单，缺陷有根因分类 |

**P0 需求全部达标，才允许发布。** P1 未达标记录进缺陷单，不阻断。
